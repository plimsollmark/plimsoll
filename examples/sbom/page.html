A signed run,
in a standard parts list.

An ingredients label, with a signed receipt stapled in. See the files that ran, the room they ran in, and what came back.{{if .Verdicts}} Further down, a referee's verdict goes into the same label.{{end}}

A bill of materials (BOM) is a parts list for software. CycloneDX is the Open Worldwide Application Security Project’s standard format for that list. This example puts one run into the list. The image’s own ingredients label is linked separately when supplied.

Plimsoll runs code in a sandbox, like a locked room. A digest is a fingerprint of some bytes, made here with the SHA-256 hash algorithm. Change one letter and the fingerprint changes. The request is the files and commands sent into the room. The result is what came back.

The daemon, a long-running server named plimsolld, returns a run record: the fingerprints, image, room’s isolation tier and times. A harness, a separate checking program, checks that record and seals it. We call that sealed record the receipt. The seal is a tamper strip, like the one on a medicine bottle.

The signed wrapper is a Dead Simple Signing Envelope (DSSE). Inside it, an in-toto statement is a standard way to write a claim. CycloneDX Attestations (CDXA) attach the receipt as evidence for the list’s three claims: code, image and isolation.

This converter needs a selected OCI manifest identity, the exact fingerprint of one container image for one platform. Today that means docker on the containerd image store. Other providers’ runs are refused when that identity is missing.

The record is signed. The BOM is unsigned. The seal lets you spot changed evidence. It does not independently measure the room’s walls. The daemon supplies those facts. A key included with the receipt shows which key checks the seal; you still need an independently trusted key to know the signer.

What a receipt holds

A till receipt for one run

Read it like a receipt

CODE and RESULT are fingerprints: a short code computed from the bytes, which changes completely if one letter changes. IMAGE is the fingerprint of the frozen filesystem the code ran in. WALL is the room. GRANT says whether the code was allowed to reach anything outside, and here it was not. TIME is the daemon's own clock.

The seal is a tamper strip, like the one on a medicine bottle: a signature over the whole receipt. Peel it, change one character, and it no longer fits. The box below this run lets you do exactly that in your browser.

The values printed on the drawing are the first run's, shortened; the full ones are in each run's section.

What sits where

An ingredients label with the receipt stapled in

Why a label

Software already ships with an ingredients label, the SBOM (software bill of materials): a list of every package inside. An AI agent's program is a new kind of ingredient with no package name, no version and no maintainer, so it never made the label. This file is that label for one run, with the receipt stapled in as evidence behind three claims.

The rows are what any viewer shows: the program and its file fingerprints, the image, the run. The staple is the part most viewers do not draw yet: the sealed receipt inside the declarations block. A platform that gives you back the original file lets you check it; this page checks it for you below.

The verdict

Did the robot go where it was told?

The receipt says what ran and where. It does not say whether the code did its job. For that somebody has to check the work, and the check has to come from the other side of the counter.

The setup, in plain words. A fleet vendor sells robots you drive through a web API (the robots are simulated; no warehouse was harmed). An AI wrote an adapter: the small program that turns the platform's orders ("robot two, go to aisle ten") into that vendor's API calls. Before the platform lets it near a real fleet it wants one answer: does the adapter do what it says it does?

So the platform runs the adapter inside plimsoll with a grant that reaches the vendor's API and nothing else, hands it a plan of four commands, and then asks the vendor what happened: which orders arrived, for which robots, and where each robot stopped. A referee compares that account with the plan under eight rules. The adapter's own report is checked against the vendor's ledger; it never gets to grade itself. The referee signs the result as a qualification statement bound to the run's receipt, and this page staples that statement into the same ingredients label as a fourth claim with a conformance score: 1 when every rule held, 0 when any broke. Conformance is CycloneDX's word for "how well the thing meets a requirement"; here the requirement is "met the platform's rules".

About the one that failed. In the scenario called lost_ack the vendor accepts robot r2's order, starts it, and then the answer gets lost on the way back (a 503, "service unavailable"). The first adapter did the natural thing and sent the order again. The robot, being a robot, did as it was told, twice. Rule four, one order per command, caught it from the ledger: run04-c2 became 2 orders (m2, m3). The rewritten adapter sends a command identifier the vendor recognizes, so a repeat is answered with the original order and the robot gets one trip. Nothing in the adapter's own report would have told you this. The ledger did, which is why the referee reads the ledger.

What this is not: an independent audit (the platform wrote the rules and signed the verdict), a real vendor (the ledger comes from the simulator the adapter example ships), or proof of who wrote the adapter. What it is: a verdict someone else can re-derive from the same evidence, which is what a score in a label ought to mean. The Go checker re-runs the eight rules from the attached statement; your browser checks the seal, the binding to this receipt, and that the claim says what the statement says. The runs, the rules and all 38 verdicts are on INTERNAL · the adapter example page →.

    The program’s own fingerprint

    Think of a file-set fingerprint as a fingerprint of the whole folder. The exact recipe follows. The file-set digest separates the program from its execution settings. Sort files by path. For each file, concatenate the 32 raw bytes of SHA-256(path) followed by the 32 raw bytes of SHA-256(content). SHA-256 of that entire concatenation is the file-set digest.

    The request fingerprint uses plimsoll.run-request.v2. The protocol is the request format revision. The result uses plimsoll.run-result.v1 and these records use plimsoll.run-record.v4, whose fields include the sandbox instance that ran the call. Each value is its length as an unsigned 64-bit big-endian integer followed by its bytes. Fields are encoded as name then value, in the reference order. Integers are decimal text, booleans are true or false, strings are UTF-8, and printed output keeps its raw bytes. The request fingerprint also covers the protocol version (the request-format revision), minimum isolation tier, timeout and software rule, so it is a different identity. The file-set fingerprint remains bound to the signed request because the checker compares the file list with the request stored in the verified bundle.

    How thick are the walls?

    An isolation tier is the kind of boundary around the code. Think of process as a cubicle, container as a room with a lock, kernel as a room with its own plumbing, and vm as a separate building, a virtual machine. These are analogies, not safety ratings.

    The reconcile runs asked for kernel. The daemon reported that tier after checking gVisor, a user-space kernel between the program and the host.{{if .VMUsed}} The same two requests, byte for byte (same request digest), were then sent to a daemon on Docker Cloud Sandboxes, which answered with tier vm: a separate building, a microVM booted from a pinned public node image.{{end}}{{if .Verdicts}} The adapter runs in the verdict section asked for container and got it; their boundary is the grant and the broker as much as the wall.{{end}} The record preserves that report. It is configuration and provider evidence plus startup checks, never hardware attestation, an independent measurement from the machine itself.

    The trust boundary

    What the checks establish

    They establish that the evidence verifies under its key, that the bundle is complete through its last checkpoint (a signed entry-count statement), and that each BOM field derived from the exchange agrees with it. -trusted-pub additionally requires the attached key to match a key obtained independently.

    What remains outside that check

    {{.Limits}}

    A score of 1 in conformance or confidence means a deterministic signature and mapping check passed. It does not mean perfect security, independent runtime assurance or a measured probability. Names, the page URL and assessor labels can be changed without re-signing evidence.

    This run’s BOM is a receipt, not a package scan. A software bill of materials (SBOM) for the image is a separate ingredients label, linked when supplied. Neither label shows that vulnerability lookups have been done. Schema validity does not establish platform ingestion or rendering. A viewer supporting these fields can display components, hashes and references; support for declarations must be tested per platform. No platform round trip has been tested here.

    Each label attaches its own line of the bundle (the stored request and response, the sealed record and the harness's signed link that places the line at its index) and refers to the whole bundle by URL and fingerprint. So a label stays small however many runs its bundle holds: the adapter bundle behind the verdicts is 1.8 MB, and each verdict label about 150 KB. The checker verifies the chain and the checks across runs when the bundle is at hand (a sibling file with the referenced fingerprint, or -check-bundle) and prints a LIMIT line saying so when it is not. Input is capped at 32 MiB.
