The ship scan

Keep the answer key out of the sandbox

When an AI agent's code is graded, the grader's own files must never reach the agent: its simulator, its hidden test cases, the seeds (single numbers each hidden case is generated from). The usual leak is not a break-in. It is a harness (INTERNAL · glossary →), the program that sets up each run and grades it, packing one of its own files into what it sends. plimsoll's ship scan checks every call on its way in, against a list of what must never get through, and stops the harness's mistake before any code runs.

The grader's notes in the same room as the work

UC Berkeley audited 13 widely used AI benchmarks and reported: “the most common pattern we exploited was submissions running in the same process, container, or filesystem as the evaluator” (EXTERNAL · article ↗). In plain words: the work being graded sat next to the grader's notes. A sandbox (INTERNAL · glossary →) keeps code from breaking out; it does nothing about what was put inside it.

So the operator of a plimsoll server, plimsolld, writes a withheld set: a file of digests (INTERNAL · glossary →), short fingerprints computed with SHA-256, of everything that must never reach a sandbox. A digest identifies a file or a value without containing it, so the set holds none of what it protects, and the daemon's log lines and refusals name an entry by its label, never by what it holds. The daemon does read each call's content, to compare it; and an audit-mode find leaves the run as it is, so code that prints a seed it was given returns that seed. The set can hold three kinds of entry:

  • a file, matched whole, under any name;
  • a file's source lines, so an edited or reformatted copy is still found once a third of its distinctive lines are there (and at least eight);
  • a value, such as a seed or a hidden answer, found as a whole run of letters and digits anywhere in the call.

The scan is the last check before a call is admitted, after the request is validated, its grant (INTERNAL · glossary →) is resolved and its isolation tier (INTERNAL · glossary →) and its software rule (the caller's requirement on which software the sandbox runs, if it set one) are met, so it only reads calls that would otherwise run.

Refuse or audit: why a hidden seed is not refused

Each entry has a mode. In refuse mode a match stops the call before it is dispatched (INTERNAL · glossary →) and tells the caller which entry matched. In audit mode the call runs, the caller is told nothing, and the operator's log names the entry.

A refusal is an answer. If an agent could guess a hidden seed, put it in its code and see the call refused, it would learn its guess was right, and it would have found the answer key by asking. So the harness's own files are set to refuse (shipping them is the harness developer's mistake, and stopping it at once is the point), and hidden answers and seeds are set to audit: a match then means the answer reached the agent, the operator voids the score, and the agent learns nothing.

Build a set for your harness

plimsoll-withheld build -mode refuse -file harness/ -source harness/ -source-mode refuse \
  -values seeds.txt -values answers.txt -values-mode audit -exempt grader > withheld.json
plimsoll-withheld scan -set withheld.json outbox/      # offline: exit 1 on a find
PLIMSOLL_WITHHELD_FILE=withheld.json plimsolld        # with your provider's settings
  • The grader's own calls must carry the harness, so its caller is named with -exempt: calls from that caller are not scanned, and their log line says so.
  • A short value's digest is as secret as the value. A ten-digit seed's digest is found by trying every ten-digit number. Publish a set of files and long values if you like, as a statement of exactly what was looked for; keep a set of seeds as private as the seeds. This page publishes its set (withheld.json) only because its seeds were made up for this run, used nowhere else, and deleted when the run ended.
  • The daemon refuses to start on a malformed set, since a set that loads with a typo scans for less than its author believes.

What it catches, and what it does not

Found
  • A withheld file under any name, and an edited, reformatted or bundled copy once a third of its distinctive lines are there.
  • A withheld value in code, file contents, file names, steps and artifact names, as written, with escapes decoded, or base64-decoded once.
  • Either one inside the archives it reads: gzip, bzip2, zlib, zip (stored, deflate, bzip2, zip64) and tar, nested.
  • Archives it recognizes and cannot read (an encrypted zip member, xz, zstd, 7z, rar): a set with a refuse entry refuses the call; otherwise it runs and its log line says the scan was incomplete.
Not found
  • Forms it does not recognize at all (raw deflate, lz4, an archive encoded twice, hex): they pass unseen, so material packed that way on purpose passes even a refuse entry.
  • A value drawn into an image or packed into its pixels.
  • Files baked into the sandbox's image, and whatever a run fetches through a grant: neither passes through a request.
  • Code rewritten line by line, a few lines copied, or a model that has memorized the answer.
  • Neither the answer nor the run record states the scan yet: a record shows what ran, not that it was scanned; the operator's log is the evidence.

Reproduce

go run ./examples/ship-scan            # build the tools, run the five calls, write this page
go run ./examples/ship-scan -verify    # check the published files offline

Run from the root of a plimsoll checkout; it builds plimsolld and plimsoll-withheld from source and needs no docker, no network and no credentials. -verify checks every claim above against evidence.json, the set's digest against withheld.json, recomputes the clean call's run record, and checks this page is what the evidence renders. The seeds differ on every run, so a rerun gives new digests and the same outcomes.
