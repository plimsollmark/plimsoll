plimsoll on Kubernetes agent-sandbox: signed runs, their bills of materials, and five refusals

plimsoll is a service that runs code an AI agent wrote and says, on every run, behind which boundary it ran. Kubernetes agent-sandbox is a Kubernetes project that keeps sandboxes as pods (Kubernetes' unit of one or more containers) in a warm pool, started ahead of time so a run does not wait for one. This page is two real runs through plimsoll on agent-sandbox, recorded on {{.Date}}, each signed and converted into a bill of materials, and five things plimsoll refused to do on the same cluster. Every claim below is either signed, and checkable with the commands at the end, or marked as a transcript.

Words this page uses

  • Tier: how strong the wall between the code and the machine is. container is an ordinary container (runc): the code talks to the machine's own kernel through a filter. kernel is gVisor: a stand-in kernel that runs as an ordinary program, so the code never talks to the machine's kernel directly. vm is a separate virtual machine.
  • Runtime class: the Kubernetes object a pod names to pick how its containers start. Its handler is a name, runsc for gVisor or runc, which each node maps to a program in its own configuration. The Kubernetes API shows the name, never the mapping.
  • Floor: the weakest tier a request accepts. A provider that cannot meet it refuses before anything runs.
  • Run record: what the daemon states about one run: SHA-256 digests (fingerprints that change if one byte changes) of the request and the result, the provider, the tier, the image, the times. A harness outside the daemon checks each record against the request and result it saw and signs it with its own key, into a bundle file.
  • Bill of materials (BOM): a parts list. CycloneDX is a standard format for it that supply-chain tools read; here each run's BOM lists the program's files, the image, the steps, and the record's claims, with the signed evidence attached.
  • Hardened mode: plimsoll's strict start. It refuses to serve unless every production rule holds: a VM or verified gVisor, a pinned image, per-caller authentication and limits, a stated memory, CPU and disk budget.

What happens on each run

Step 4 is new. A handler's name is configuration on each node, which the Kubernetes API does not show, so before any of the run's code plimsoll runs one command of its own in the claimed pod, as the guest: the first line of the kernel log, which under gVisor is gVisor's own boot line, and the seccomp mode, which under runc must show a filter. The pod is fresh, so nothing of a guest's has run in it yet. On this cluster the check cost nothing measurable: the median snippet took 75 ms from claim to result with it and without it, over ten runs each. Refusal 4 below is why it exists.

Check it yourself

From a checkout of the repository. The first command checks every signature, digest and link in the bundle; the second rebuilds a bill of materials from the signed line it attaches and compares it, pinning the harness key you trust.

go run ./cmd/plimsoll-attest verify -pub docs/examples/agentsandbox/harness.pub docs/examples/agentsandbox/bundle.jsonl
cd examples/sbom
go run . -check ../../docs/examples/agentsandbox/{{(index .Runs 0).BOM}} \
  -trusted-pub ../../docs/examples/agentsandbox/harness.pub \
  -check-bundle ../../docs/examples/agentsandbox/bundle.jsonl
cd ../..
go run ./examples/agentsandbox   # writes this page again from the files beside it

The harness key is the CycloneDX example's (key ID {{.KeyID}}): one operator's harness signed both pages' runs.

How this was recorded

  • A kind cluster (Kubernetes in docker, one node) on one developer machine: Kubernetes 1.37.0, containerd 2.3.4, agent-sandbox v1.0.7, gVisor release-20260907.0.
  • The pool's template is the one in EXTERNAL · source repo ↗, with the image pinned by the digest above and plimsolld's network as the only source allowed in.
  • plimsolld ran in a container on the cluster's network, since it reaches each pod's sandboxd at the pod's address, in hardened mode: a callers file, the pinned image required, 256 MiB, 1 CPU and 160 MiB of disk per run, 60 runs a minute per caller.
  • Refusals 4 and 5 needed root on the node: its containerd configuration was edited, which no caller and no pod can do. They stand for a node that joins a pool misconfigured, not for an attack.
  • The operator guide is EXTERNAL · source repo ↗.

What this does not show

  • A tier is configuration and provider evidence plus these checks, never attestation. gVisor's boot line is text a node's root could forge; the check catches a misconfigured node, not a hostile one.
  • One node on one machine. On a cluster of many nodes, each run's own check covers the node it lands on, and the startup smoke test covers only the nodes its two pods landed on.
  • Memory: on a node with swap, a gVisor pod can hold more than its limit (measured on this cluster: a 128 MiB pod held 1024 MiB, 932 of it in swap, where runc killed the same pod at 112 MiB). That is gVisor's open issue 15756, not something plimsoll can see from the API; the operator guide gives the node setting that stops it.
  • The refusals are transcripts. Only the two runs are signed.
