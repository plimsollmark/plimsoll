Prime Intellect's verifiers, on plimsoll

Prime's own task ran unchanged on plimsoll, and every call left a record you can recheck

verifiers (EXTERNAL · source repo ↗) is Prime Intellect's Python library for the environments AI models are trained and tested in. Its runtime is the place a task's commands run and its files live. plimsoll's runtime plugin makes that place a plimsoll session (INTERNAL · glossary →), one sandbox (INTERNAL · glossary →) kept open for the whole attempt, so every command runs behind plimsoll's walls and comes back with a run record (INTERNAL · glossary →), plimsoll's statement of what was sent, what came back and where it ran. On this page Prime's own task uuid_ctf, a puzzle solved with shell commands, ran through it unchanged. The model in these runs is a script, not an AI, as the box below the picture explains.

The “model” on this page is a script, not an AI. A small server on the evaluator, the machine running verifiers, answers each of verifiers' model requests from a fixed list of moves (the server (EXTERNAL · source repo ↗), the moves (EXTERNAL · source repo ↗)): it reads the last tool result and makes the next planned call. That keeps the run free and repeatable while it drives verifiers' real loop, real model-call plumbing and real runtime calls. So every number here measures the plumbing: verifiers, plimsoll and the task. None of them says anything about how well an AI model would do the task.

The headline numbers. A reward is verifiers' score for one attempt, from 0.0 (failed) to 1.0 (solved). runc (INTERNAL · glossary →) is docker's usual container runtime, and gVisor (INTERNAL · glossary →) is Google's stand-in kernel, which answers the code's requests to the operating system itself: the two walls the sandbox ran behind.

The 30-second version

1

verifiers' command vf-eval runs a task for a model. Whenever the model wants a command run or a file read (a tool call), verifiers asks its runtime.

2

With plimsoll as the runtime, each of those is one call to plimsolld, the plimsoll server, which runs it in the session's sandbox and answers with the output and a run record.

3

The client checks each record as it arrives and appends it to a log. Later, anyone can recheck the whole log with nothing but the file.

The taskPrime's uuid_ctf, from their own environments repository (EXTERNAL · source repo ↗), unmodified: find a recovery token in a synthetic incident archive with shell commands and write it to /workspace/answer.json.
The harnessIn verifiers, the harness is the agent program: the loop that sends the conversation to the model and carries out its tool calls. Here it is plimsoll-bash, verifiers' own bash harness with its loop on the evaluator (why, below).
The runtimeplimsoll's plugin, plimsoll_client.verifiers_runtime: each command, read and write is one call of one plimsoll session.
The graderThe task's own scoring code, which reads the answer back from the sandbox after the attempt.
The record logA file of one JSON line per call: each record's digests (INTERNAL · glossary →), SHA-256 fingerprints of the request and the result, and the isolation tier (INTERNAL · glossary →) the call ran behind. Never the command text.

What ran

Every configuration below ran fresh, in one go, from one command (at the end of this page). On plimsoll every attempt asked for a floor (INTERNAL · glossary →), the weakest tier it accepts: container under runc and kernel under gVisor. vf-validate is verifiers' own check of an environment, run here on plimsoll-sum, a tiny test environment of plimsoll's: the gold (known correct) answer must pass, and the task left untouched must score 0.0 when graded in a fresh sandbox that received only its output files. A run where a script deliberately writes a wrong answer has to score 0.0 too, or a 1.0 means nothing.

Why plimsoll-bash, and not the shipped harness

verifiers' shipped bash harness, on plimsoll, never reached the task: {{if .Error}}it stopped in its own setup with {{.Error}}{{else}}it ended with {{.Stop}}{{end}}. Every harness verifiers ships installs itself inside the runtime from the internet and then calls the model from inside it, and a plimsoll sandbox has no network at all. plimsoll-bash runs the same loop on the evaluator instead: verifiers' own chat loop from the shipped bash program, loaded unedited, with each bash or edit call sent to the sandbox as one session call. verifiers' harness contract allows a loop to run outside the runtime as long as every model call goes through verifiers' own endpoint, and this one does. For an environment's author it is one line of configuration, --env.agent.harness.id plimsoll-bash, not a change to the environment.

The limits, stated plainly

These come from the plugin's own documentation (linked at the end of this page). This run met two of them head on: the network, in the shipped harness's setup, and the work directory, in uuid_ctf's /workspace.

  • One image. A plimsoll server runs the one image (the packaged file system a sandbox starts from) its operator configured. A task that names an image of its own is refused at start, before any of its code runs, with a message naming both. This run's image is plimsoll's Python image plus bash and a /workspace link, {{.Ev.Image}} ({{shortID .Ev.ImageID}}).
  • No network, in any phase. A task that asks for a host on the internet is refused before anything runs; a setup or grading script that downloads something fails with its own error.
  • One work directory: the session's /work, or a path the image links to it. uuid_ctf works in /workspace, which this image links to /work; the runtime checked that inside the sandbox before the task started. The rest of the file system is read-only.
  • No background processes. Whatever a call leaves running is ended before the next call, so verifiers' run_background is refused, and with it a task's tool servers and long-running helpers.
  • A call cut short ends the session's use. When verifiers' time limit cuts a call in flight, the client stops using that session (the call may have run), so the attempt ends as an error rather than a score; the record log lists the session as incomplete.
  • Throughput. plimsolld's default limit is 30 runs a minute per caller{{with .Gold}}, about two attempts a minute at this task's {{len .Chain}} calls each{{end}}; this run raised it (SANDBOX_RATE_PER_MIN=600).

What this proves, and what it doesn't

Proves
  • An outside verifiers task, unmodified, ran its setup, every tool call and its grading in plimsoll sessions{{if and .Gold .Docker}}{{if eq (reward .Gold.Reward) (reward .Docker.Reward)}}, and scored what verifiers' own docker runtime scored ({{reward .Gold.Reward}}){{else}}, and scored {{reward .Gold.Reward}} where verifiers' own docker runtime scored {{reward .Docker.Reward}}{{end}}{{end}}.
  • The grader still says no: the scripted wrong answer scored {{with .Wrong}}{{reward .Reward}}{{end}}.
  • Every call left a run record, and every log rechecks offline: each record's digest recomputed from its fields, each session's chain unbroken, each closed session's call count matching the server's. Two separate checkers agree on every count: the Python client's check_record_log and this program's Go checker.
  • The tier plimsolld reported for every call, each at or above its attempt's floor (the Go checker refuses a log otherwise): container under runc, kernel under gVisor.
Doesn't prove
  • Anything about an AI model. The moves were scripted. A run with a real model is the next step, and it is not on this page.
  • Who wrote the log. A record log is not signed: rechecking shows the records agree with each other and nothing was changed or dropped without it showing, not who produced the file. The Nemotron example (INTERNAL · example page →) signs every call.
  • Conformance. verifiers' runtime conformance suite (tests/unit/test_runtimes.py in their repository, not in the installed package) was not run. Reading it suggests the background-process, task-image and network-policy cases would fail by design; that is a reading, not a result.
  • That the hardware is honest: the tier is the server's configuration, the provider's evidence and its startup checks, not a hardware attestation.
  • That other verifiers environments run on plimsoll. One that names an image of its own is refused, and this run measured only Terminal-Bench 2's (above).

Run it yourself

From a clone of the repository (EXTERNAL · source repo ↗), with docker, gVisor installed as docker's runsc runtime, and Python {{minor .Ev.Python}}:

make docker-images                         # plimsoll's sandbox images
make py-frameworks PY_FRAMEWORKS=verifiers # the hash-locked verifiers environment
go run ./examples/verifiers                # every configuration above, fresh; rewrites this page
go run ./examples/verifiers -verify        # recheck the files beside this page; starts nothing

The program fetches the two outside repositories at their pinned commits and refuses any other: prime-envs at {{short .Ev.Task.Commit}}, whose task files it also checks by SHA-256 because the task's own scoring code runs on the evaluator (as verifiers runs every task), and Terminal-Bench 2, which it only reads. It spends nothing: no model, no paid sandbox. Everything on this page comes from evidence.json and the record logs beside it:
