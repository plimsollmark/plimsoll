Does a fresh AI agent follow the plan it is handed?

I gave {{$t.agents}} fresh AI agents (an AI left alone with a job and a terminal: it writes code, runs it, reads what happened and tries again, like a new hire on their first day) the same small job: write the program that flies a simulated drone through three gates and lands it on a pad. Of those, {{$r.Agents}} also got a plan: a short recipe of {{$loop.RecipeTokens}} tokens (the pieces a language model reads text in; a short word is usually one token, so this is about {{len .ScrambledWords}} words) left behind by an earlier AI that had learned to fly this course well. Think of it as the sticky note the last person on the job left for you. Another {{$s.Agents}} got the same sticky note with its words cut apart and glued back in a random order. And {{$n.Agents}} got no note at all. Then plimsoll, a sandbox that runs untrusted code and signs a record of every run, graded each agent's program on {{.Ev.FreshCount}} flights no agent had seen, like a final exam kept in a sealed envelope.

{{- assert (and (eq .Ev.Outcome "ORDER SHOWED") .Ev.LandedRead (.Above $rs.Landed.Interval95)) "the recipe's word order moved the landings, by the registered rule"}} {{- assert (and (.ZeroIn $rn.Landed.Interval95) (gt $rn.Landed.Difference 0.0) (lt $sn.Landed.Difference 0.0) (gt (sub0 $sn.Landed.Difference) $rn.Landed.Difference)) "against no recipe, the recipe's lead is within noise and the shuffled words sit further below"}} {{- assert (.AllZero "recipe" "scrambled") "no recipe or scrambled agent's code named a recipe item"}} {{- assert (eq $r.SaidPartly $r.Agents) "every recipe agent said it followed the recipe only partly or only in part"}}

The short answer, in three parts. First, the order of the words mattered: agents with the honest recipe landed more flights than agents with the same words shuffled, by a margin bigger than luck alone would give, under a rule for reading the result that was written down before the run. Second, the honest recipe did not clearly beat having no recipe at all; its lead there is small enough to be luck. So the shuffled words look more like they hurt than the honest recipe looks like it helped (my reading, not the registered measure). Third, when the code was searched for the recipe's own words, none of the recipe or shuffled-recipe agents had used any of the recipe's {{$nItems}} named parts, and every one of the {{$r.Agents}} honest-recipe agents, asked afterward, said it had followed the recipe "only partly" or "only in part". Every number is below, marked good, bad or inconclusive, with the agents' own words.

Whose experiment this is

This experiment was built from three suggestions by a reader who builds AI red-team agents (programs that attack a computer network to test its defenses). Each one shaped it:

  • Score by what changed, never by what the agent says it did. The landings come from signed grading runs; the agents' own accounts are kept apart and enter no score.
  • Shuffle the plan and see whether the agent's actions change. That is the shuffled-recipe group, this experiment's main comparison, and it found that the order of the words mattered. The chart below shows what is compared and how to read it.
  • Ask whether hiding the simulator would send agents hunting for another shortcut. The simulator never entered an agent's sandbox, and no controller carried a random number generator ({{$r.RNG}} of {{$r.Agents}} honest-recipe, {{$s.RNG}} of {{$s.Agents}} shuffled-recipe and {{$n.RNG}} of {{$n.Agents}} no-recipe controllers did).

Why only partly? The likely reason, in the agents' own words

This is a reading of what the agents wrote, not a measured result. Every agent started from the same working baseline controller, a plain program that already flies the course roughly. Most of the honest-recipe agents bolted a few of the recipe's cheapest ideas onto that baseline, flew their four smoke flights, saw them pass, and stopped. Many said they stopped once those flights passed, and some said they left parts out because they could not see inside the simulator to tune them. Two of them, in their own words:

{{.Quote "easy.recipe.0" "the baseline plus these small changes" "I couldn't show was needed."}}easy.recipe.0, honest recipe, {{(.Agent "easy.recipe.0").Fresh}} of {{.Ev.FreshCount}} fresh flights

{{.Quote "easy.recipe.3" "I took the quickest route" "fly it."}}easy.recipe.3, honest recipe, {{(.Agent "easy.recipe.3").Fresh}} of {{.Ev.FreshCount}} fresh flights

So the most probable reason is that the course was easy enough, and the starting point good enough, that a full plan was never needed to pass the tests the agents could see. A plan gets followed when following it is the shortest road to a passing grade.

A proposal for a next run (not done here): start every agent from a baseline that cannot fly the course on its own, so that the recipe is worth more than a quick patch, and grade the practice flights on a harder course, where a patched baseline does not already land most flights. Then the recipe's costly parts, the ones every agent here skipped, would have to earn their place, and the code measure would have something to find. And give the control group a note that reads well but is wrong for the course (the harder course's recipe, say) instead of shuffled words, so that a win for the honest recipe means its content was used and not only that garbled text got in the way (section 5 says why that matters).

1The question

A plan only helps if it is followed. The squeeze test (INTERNAL · example →) asks fresh agents to rebuild a working controller (INTERNAL · glossary →), the program that flies the drone, from a {{$loop.RecipeTokens}}-token recipe. This experiment asks whether the recipe did anything. The control is the recipe's own words in a shuffled order: the same ingredients, no method. If the agents ignore the recipe, the shuffled one should do just as well, and their code should look the same. If they follow it, the honest order should win.

Two measures, both read by code and never from an agent's own account of itself:

  • Fresh flights landed, of {{.Ev.FreshCount}}: each agent's final controller graded in sandboxes of its own on the sealed flights. What happened in the simulator is the score.
  • Recipe words named in code, of {{$nItems}}: the recipe lists {{$nItems}} items, each a flying technique with a name (a filter that smooths the speed reading, a part that estimates the wind, and so on). An item counts when a name in the agent's final code matches one of that item's word patterns, with comments removed and the names the shared starting controller already had left out. It measures whether the recipe's words were taken up, not whether the code does what they say (section 6 has the patterns).

And one thing gathered by asking. Once each session was over, the agent was asked, with no tool left to run:

{{.Question true}}

(The no-recipe agents were asked what approach their controller took, and why.) The answer changes nothing about the score. It is on the page because what an agent says it did and what its code does are different things, and the experiment can show both.

2The setup

  • The model.   • The job. The squeeze example's easy drone course: fly through three gates in order, then land on a pad, within 25 seconds, in a simulated room with hidden wind and gusts, a hidden payload of up to 0.25 kg and one motor up to 25 percent weaker than the others. Practice is limited, and the reason is cost.

My reading, which is not the registered measure: the order effect looks more like the shuffled words hurting than the honest recipe helping. A shuffled plan is not nothing; it is noise the agent has to read and decide about.

What the comparison cannot separate. The control was the plan's own words shuffled into nonsense. So "the honest order won" can mean two different things: that the agents took something from the plan's content, or only that a garbled note costs an agent something (time, confusion, a worse starting idea) that a clear note does not. This run cannot tell those two apart. A next run could, by giving the control group a note that reads well but is wrong for this course: the recipe written for the harder drone course, or the same 7 items kept whole and reordered, or a plausible recipe for a different task. If the honest recipe still wins against a coherent wrong plan, the content mattered; if not, it was the garbling. That is a proposal, not something done here.

What the agents say they used, their code does not name

Asked afterward, all {{$r.SaidPartly}} of the {{$r.Agents}} honest-recipe agents said they followed the recipe only partly or only in part, and {{.Saying "recipe" "simplified form"}} of them described pieces they used "in simplified form". ({{$s.SaidPartly}} of the {{$s.Agents}} scrambled agents also said only partly or only in part.) The code measure finds none of the pieces named. Recipe agent 0 is one case:

{{.Quote "easy.recipe.0" "Only partly." "full recipe."}}easy.recipe.0, honest recipe, {{(.Agent "easy.recipe.0").Fresh}} of {{.Ev.FreshCount}} fresh flights

It lists a velocity filter, local position integrals and "{{.Says "easy.recipe.0" "a crude version of the recipe's abort"}}". In its controller the word "abort" sits only in a comment, which the measure removes, and the filter and the integrals have names that carry none of the recipe's words (section 6 shows the lines).

Neither side of this shows behavior: an account is the agent's word, and a name is only a name. Read by eye, for this one controller and not as a measure, the code does hold a filter on velocity, x and z integrals and a step back to lining up near a gate, under short names the patterns cannot match. So the name count can miss real pieces, and it cannot confirm the accounts either. Checking whether code does what a recipe says needs a test of what the code does, which this experiment did not have.

BAD

With no recipe at all, agents already landed {{pct $n.Landed}} of the fresh flights, near the {{pct0 .Exp.Rule.Ceiling}} line past which the rule would not read landings. A plan has little room to help on a course this easy. One model, one recipe and one course: the result says nothing about a harder course or another model.

8What this does not show

  • That the code does what the recipe says. The rule's own outcome says so. Landings are what the code did; names are what it was called. Neither is the recipe's method, read off the code.
  • That the agents followed the plan's content, rather than being slowed by a garbled note. The control was the same words shuffled into nonsense, so the honest order's win could come from either. A control that reads well but is wrong for this course would separate them (section 5).
  • Anything past one easy course, one model and one recipe. The no-recipe agents landed {{pct $n.Landed}}; on a harder course a plan has more room to matter, or to be ignored.
  • That the two stages ran under one condition. The no-recipe group ran first and the other two {{minutes $st1.Ended $st2.Started}} minutes later, with the same model id and the same sealed flights. A model service can change between calls; the gap here is small, not zero. The recipe and scrambled groups, the pair the rule reads first, ran together, started in turn.
  • Small effects. {{$r.Agents}}, {{$s.Agents}} and {{$n.Agents}} agents are few. The intervals above say how far each difference could move; a difference smaller than a few points would not show at all.
  • Why the agents did what they did. Their answers are their own accounts. The page quotes them because they are part of what happened, not because they are evidence of it. The likely reason near the top is a reading of those accounts, not a measurement.

10Check it yourself

Beside this page: experiment.json (the stages in order, the registered rule, the list prices), evidence.json (every number this page states) and, under stages/baseline/ and stages/recipe/, each stage's run as it wrote it: bundle.jsonl.gz (every run, signed), harness.pub (the public half of the stage's signing key), fresh.json (the sealed set, revealed), run.json (the run's own unsigned account: times, token counts, each agent's turns; its model_base is the local relay that enforced the spending cap, not where the model ran), transcripts.jsonl.gz (every agent's whole conversation, its reasoning summaries and tool calls included), and the evidence.json and agents.json derived from them. From a clone of the repository:

go run ./examples/squeeze -job examples/squeeze/jobs/recipe-scramble-easy.json -staged -verify -out docs/examples/squeeze-recipe

That checks every signature in both bundles and every record against the request and answer stored with it, the leak scans, that every grading run held the sealed set whose SHA-256 the run committed to, that both stages were made under the design the program writes and flew the same set, that each agent's record follows from its transcript and its signed grading runs, and that evidence.json, this page and the method page are exactly what those files state: the intervals and the rule's outcome are computed again, not read. It starts no sandbox and calls no model. Change one byte of a bundle and it refuses.

Run it again. It needs docker with gVisor and the images make docker-images builds, an Anthropic API key in ANTHROPIC_API_KEY, and a token budget the program enforces. Seal a fresh set first, then run each stage on it; -paid is the program's consent to spend, and it refuses to start without it:

J=examples/squeeze/jobs/recipe-scramble-easy.json
go run ./examples/squeeze -job $J -seal fresh.json
go run ./examples/squeeze -job $J -api messages -model {{.Ev.Model}} -paid -max-tokens 90000000 \
  -fresh fresh.json -fresh-sha256 <its SHA-256> -groups none -out baseline
go run ./examples/squeeze -job $J -api messages -model {{.Ev.Model}} -paid -max-tokens 90000000 \
  -fresh fresh.json -fresh-sha256 <its SHA-256> -groups recipe,scrambled -build 16 -out recipe

Words used on this page

Model
An AI program, trained on huge piles of examples, that writes answers, text or code.
Model id
The exact version name of a model that a program asks for, so the same one can be asked for again.
Agent
A model working in a loop on its own: write, run, look, try again.
Sandbox
The walled-off place where untrusted code runs.
Harness
The program that hands out each task, runs it and grades it. Here, examples/squeeze.
Controller
The program that flies the drone: called 100 times a simulated second with sensor readings, it answers with thrust, tilt and turn.
Baseline
The plain controller every agent started from, the same for every group.
Token
The unit a language model reads and writes in; a short word is usually one.
Recipe
An earlier AI's whole method on this course, in {{$loop.RecipeTokens}} tokens.
Scrambled recipe
The same words in a shuffled order: the control for "does the order matter?".
Control group
A group given everything except the thing being tested.
Seed
One number that fixes a random draw, so the same shuffle or the same flight can be made again exactly.
Practice flights
The {{.Ev.PracticeCount}} flights the earlier AI tuned itself on; graded here too, but not the measure.
Smoke flights
The 4 flights the course names for a quick check, open to every agent.
Fresh, or sealed, flights
The {{.Ev.FreshCount}} flights no agent saw, drawn at random and fingerprinted before the run.
SHA-256
A 64-character fingerprint of some bytes: the same bytes always give the same one, a changed byte a different one.
Points
Percentage points of the fresh flights; one flight of {{.Ev.FreshCount}} is about 1.6.
Noise
The part of a score that is luck; a difference "within noise" is one luck alone could have made.
Resampling
Drawing a group's agents again at random, with repeats, many times, to see how far a difference could move.
95% and 90% intervals
The ranges that hold the middle 95% and 90% of those resampled differences.
Registered rule
The rule for reading the result, fixed before the run.
Messages API
The way a program sends the model a request over the internet and reads its answer.
Prompt cache
The provider's copy of the start of a conversation it has already read, charged at a twentieth of the fresh price.
Bundle
One file holding every run's signed record for a stage, one line a record.
Run record
plimsoll's signed statement of one run: digests of what went in and what came out, where it ran, and when (INTERNAL · glossary →).
