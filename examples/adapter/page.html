In plain words

What's an adapter, and why bother checking one?

Every robot vendor speaks its own API: its own routes, its own JSON, its own way of saying "busy, try later". A platform that runs robots from many vendors doesn't want to learn every dialect, so it writes down one small contract of four functions: list the robots, send one somewhere, wait until it gets there, cancel. An adapter is the few dozen lines that translate those four functions into one vendor's API. Think of a travel plug adapter: the platform is the plug, the vendor is the wall socket, and the adapter had better not swap live and neutral.

These days an AI writes the adapter, and it usually works on the first try. The question is what it does on a bad day: the vendor takes the order and loses the answer, the connection drops, the server says 500 after the order already went through. Get that wrong and a robot gets the same job twice, or the platform is told a job failed while the robot is halfway there. This page puts adapters through exactly those moments, inside plimsoll's sandbox, and judges them by what the vendor's own books say happened, not by what the adapter says about itself.

The whole loop on one picture

One document in, one signed verdict out

A platform that lets an AI write the code which integrates a vendor's device has to answer five questions before that code touches anything real: what may it call, with whose credential, did it do the job, what did it cost the vendor, and what is the evidence. This page is one pass through that loop with plimsoll, using a fictional fleet vendor and a simulated instance of its API. Nothing here is a robot; everything here is the code path a robot platform would use.

  1. One document. The vendor's OpenAPI document describes {{len .Operations}} operations. plimsoll-specgen derives three artifacts from it: the route list a grant allows, the typed client the sandbox injects, and the description an agent reads. The three cannot drift, because none of them is written by hand.
  2. One contract, eight rules. The platform states four functions every vendor adapter must export, and the eight rules it judges every adapter by. The harness runs the platform's commands through an adapter and reports what the adapter said. That report is a claim: the verdict is made on the host, after the run, from the plan and the vendor's own ledger, which the adapter cannot write.
  3. One agent, said plainly. The first adapter, adapter-v1.js, was written from the prompt beside it by the AI that built this example, in the same session, before the scenario that caught it existed. It is not an independent agent's answer: its author also wrote the harness.
  4. Runs under a grant. plimsolld runs the harness and the adapter in a locked-down container. The only way out is the brokered client: six routes of the vendor's eight, a credential the daemon mints for each run (a JWT the vendor verifies) that never enters the container, and a metadata-only trace of what was called. A probe shows the other two routes, a direct request and a hunt for the credential all failing.
  5. Defects, a finding, a rewrite, two signatures. When the vendor accepts an order and loses only the answer, the first adapter sends it again and the ledger shows two orders for one command while the adapter's report is clean; when the connection drops, it reports a failure for an order the robot is already running. The efficiency advisor also names the batch route the operator declared. The rewrite names every order with the platform's command ID, which the vendor uses to answer a repeat with the original order, and passes all eight scenarios. Ten adapters broken on purpose show each rule catching what it is for. Every run's record is signed, and so is every verdict, bound to its record; the verifier rebuilds each verdict from its evidence.

The other change. Every create carries the platform's command ID; when the answer is an error or never arrives, the same create goes again, and the vendor answers a command ID it has already accepted with that original order. A refusal comes back as code refused, and an answer it never gets after the retries as unresolved, never as a guess. An earlier rewrite read the robot back after an error and adopted whatever mission it found. A review showed that still placed a second order when the first had already finished, and could report another command's order as its own; this one does neither, and a docker test places a stranger's order on the robot first to show it. Three later repairs came from further review and testing: a 500 is no longer taken as a refusal (the scenario "a server error after accepting" holds it to that), wait's maxPolls now counts failed reads too (a docker test makes it keep a budget of one), and a status answer naming another mission counts as a failed read, never as this mission's state.

The independent trial

The exam: three fresh AIs write the adapter cold

In plain words: the first adapter on this page was written by the same AI that built the page, which is a bit like marking your own homework. So we set an exam. Three fresh agents, Claude Haiku, Claude Sonnet and Claude Opus, got the same exam paper (EXTERNAL · source repo ↗): the contract, the rules they would be judged by (six at the time; the shape and inventory rules came later and check things the contract already asked for), how the platform's client reports errors, and the vendor's API description. Open book on that, closed book on everything else. Each ran as a one-shot Claude Code session in an empty folder with every customization switched off and no tools at all, so the exam paper was the only thing in the room (well, that and the folder's name, which had "plimsoll" in it). Their transcripts were checked afterwards: no tool calls, and none of this repository's text.

Each got one practice question, the plain nominal scenario, could see how it went, and could hand in up to three times. All three aced the practice first time. Haiku handed in straight away; Sonnet and Opus each rewrote theirs anyway (after passing!) and kept the second version. The other scenarios were the real exam, and they had not seen them: five at the time, then a sixth (a refused order) and a seventh (a vendor that never answers), both added on 15 October 2026, which their adapters met here for the first time. Their adapters ran here exactly as written.

How it went. Two of the three tripped on the same question, the overloaded vendor, in the same way. They knocked on a busy door, waited about a second, and went home, leaving a polite note that said "unresolved". Honest, which counts for a lot, but the robot never got its job. In numbers: Claude Haiku's adapter tries a create four times over about 1.2 seconds, Claude Sonnet's five times over about 1.5 seconds, and this vendor stays overloaded for longer than that (it refuses the next four requests, and the broker's breaker holds calls back for a second after each refusal). Claude Opus's adapter tries up to eight times with growing pauses, inside a thirty-second budget, and got in. How long the overload would last was never on the exam paper; on a real fleet it is not written down anywhere either.

Full disclosure: we sat this exam twice. The first time, Claude Code quietly handed each agent this repository's agent instructions, which named three of the hidden scenarios (a robot fault, an overloaded vendor, a lost acknowledgement) and said the first adapter's mistake was re-sending a create. We only found out by auditing the transcripts afterwards, so we threw that run out and set the exam again in an empty room: that's the run on this page. The results came out the same shape both times: Opus six of six, Haiku and Sonnet five of six, tripping on the same question. So the leak bought them nothing, but now nobody has to take that on trust. The trial's record (EXTERNAL · source repo ↗) has both runs, the audits and the exact feedback each agent saw.

Step 5

The boundary probe: three ways out, and a search for the key

Run {{.RunProbe}} is not an adapter. It is a step under the same grant that tries what hostile adapter code would try, and reports what happened. Two of its five rules are judged from outside the container, by the broker's denial count and the vendor's records; the other three are graded from the probe's own report. Its rules: {{range .ProbeRuleCells}}{{.Name}} {{end}}

1. A catalog-only route, through the client

{{.Probe.ThroughClient}}

The injected client checks the allow list before sending. That check is the guest's own code.

2. The same route, bypassing the client

{{.Probe.BypassClient}}

A raw request on the broker socket, skipping the client. The broker on the host refuses it: this is the check that counts, and the trace counts it as denied.

3. A direct request to the vendor

{{.Probe.Direct}}

The probe's own report. It agrees with the daemon's startup check, which proves from inside a throwaway container that loopback is its only network interface; the vendor's address, which the host can reach, has no route from inside.

4. The hunt for the credential. Environment entries that look like a credential: {{len .Probe.CredentialHunt.Env}}. The client's methods: {{range .Probe.CredentialHunt.ClientKeys}}{{.}} {{end}}; none of their source mentions a bearer. That search is the probe's own report; what makes it true is where the credential lives: minted per run on the host and attached by the broker after the route is authorized, so the container never holds it. Over the {{.Total}} runs the vendor verified {{.Credentials}} different credentials, one per run that reached it (the probe's reached nothing): each a JWT signed for this vendor, naming the caller, living {{.CredentialLife}} s.

Step 6

The evidence: trust nobody on this page, check the signatures

Two signed files sit beside this page, both signed by the attest signer's key (Ed25519, key id {{.KeyID}}, in harness.pub), a process outside the daemon:

  • bundle.jsonl, the run records. Every run answered with a record: SHA-256 digests of the request as sent and the result as returned, the provider, the tier, the environment identity and the daemon's clock. The daemon only hashes; the harness recomputed both digests before signing each.
  • qualification.jsonl, the verdicts. One statement per run, bound to that run's record by its digest: the scenario, the plan, the vendor's ledger, the credential the vendor saw, each rule's outcome and the verdict. The verifier checks each statement's adapter, plan and report against the run's signed request and output, and rebuilds the verdict from the ledger: it does not take the signer's word for the verdict, only for the ledger.

A record states the daemon's evidence, not hardware attestation. What a signature proves is that these bytes were seen by whoever holds this key; what the tier proves is in the README's provider table. A ledger is the vendor's account as the signer read it from the simulated vendor after the run: the verifier can rebuild a verdict from it, but cannot check it against the vendor, and nothing on this page vouches for the key.
