Two pizzas, one order: the lost-answer bug

Carroll Guertin, 2026-10-16

You order a pizza. The line drops right after "got it". You call back and order again. Two pizzas arrive.

AI-written code makes this mistake with robots. Below is one run from a small example I built: the bug, how a grader catches it without trusting the code, and what my sandbox, plimsoll, added.

The setup

Platforms now let AI write adapters: the code that turns the platform's commands into calls to a vendor's API. Here the vendor runs warehouse robots.

whowhat it is
🏢 the vendorfleetsim, a robot fleet simulator I wrote, with three robots (r1, r2, r3)
🔌 the adapterAI-written JavaScript that places and tracks orders with the vendor
📦 the sandboxwhere the adapter runs: no network, no access to my machine
🛂 the brokerplimsoll's gatekeeper: forwards 6 of the vendor's 8 operations and adds a key made for this run only
📒 the ledgerthe vendor's own list of every order it accepted
⚖️ the grader8 rules checked after the run against the ledger and the robots, never the adapter's report
🧾 the receipta signed record of what went into the sandbox and what came out

Every order can carry a command_id, an order number. The vendor's API spec says a repeat with a number it already accepted returns the original order instead of making a new one.

A harness gives the adapter the same four commands in eight scenarios: a normal day, a robot that faults mid-order, a robot out of service from the start, an overloaded vendor, and four ways to lose an answer. Then the grader checks eight rules. One is one_order_per_command.

The lost answer

In the lost_ack scenario the vendor accepts r2's order, starts the robot, then answers 503 "acknowledgement lost". The order exists, but the adapter is told it failed.

The first adapter, adapter-v1.js, retries without a command_id. The vendor can't tell a retry from a new order, so it creates a second one, m3. Robot r2 drives to (10,4) twice. The adapter reports "all done".

The second adapter, adapter-v2.js, retries with the same order number. The vendor answers "that's m2" and nothing else happens.

The vendor's event log for that command (numbers are positions in the log):

The grader fails the first adapter on one rule of eight: "run04-c2 became 2 orders (m2, m3)". The second passes all eight. Replay the first run and the second on the example page and watch r2 do its extra lap.

A caveat: I wrote adapter-v1.js in the same session that built the example, so it isn't an independent trial. When Claude Haiku, Sonnet and Opus each wrote an adapter from the contract in a clean session with no tools, all three used the order number. The point isn't that AI gets this wrong. It's that you can check without taking the adapter's word for it.

When nobody can know

In the silent scenario the vendor accepts the order, then its gateway answers 504 to every request about that robot. The adapter has no way to learn whether the order went in.

The second adapter tries 40 times, a quarter second apart, then reports unresolved: "the vendor may or may not hold the order". That's the honest answer, and the contract asks for it. (The vendor does hold it, as m2.)

The example also has ten adapters broken on purpose. One gives up after three tries and reports refused, which tells the platform it's safe to order again. The grader fails it on report_is_true because the vendor holds the order as m2. Believe it, and you get two pizzas.

What plimsoll did, and didn't

plimsoll didn't prevent the double order. No sandbox stops code from ordering twice when ordering is its job. It controls what the code can reach while it runs, and makes the verdict checkable afterwards.

The usual way to test an AI's adapter is to run it on a laptop, in CI, or in production. There it has your files, your network and the vendor's real key, and its "all done" is believed. The two pizzas show up in production.

The right column was tested, not assumed. A probe ran under the same grant and tried what hostile code would: a direct call to the vendor got ECONNREFUSED, a raw DELETE /robots/r1 got 403 from the broker, and a search of its environment and client found no key, because the broker adds it outside the sandbox. Across 51 runs the vendor saw 50 keys, one per run that reached it, each valid for 95 seconds. Under overload, the broker held calls back for a second after each 503 so retries couldn't pile on.

The grader is ordinary code you could write without plimsoll. The hard part without it is running that check on code you don't trust, with your real key out of reach, and handing someone the evidence.

I learned the first row the hard way. In both trial runs, on 14 and 15 October, the helper that gave each AI agent practice feedback ran its draft adapter with my machine's own Node, outside any sandbox. A security review caught it two days later. Nothing bad happened, by luck. The helper now runs adapters in the sandbox through the broker, and a test checks that an adapter can't read a planted secret or list my home directory.

The receipt

Every run and every verdict is sealed into a signed record: a hash of exactly what went into the sandbox and what came out, signed with a key the test run made for itself. You can check a single line from a clone of the repo. This is the second adapter's lost-answer run:

$ go build -o plimsoll-attest ./cmd/plimsoll-attest
$ cd docs/examples/adapter
$ ../../../plimsoll-attest verify-entry -pub harness.pub -line 13 bundle.jsonl
entry verified: line 13, signed by key 02c7b7eed354d6297e60f1f69eb7579acc1fcdc5a35cd1c398f05ddf5fd94fc7: record 3c54bdfe1ccb0b753d9e44238afc250fc7e7212f5aa444242f5fe59319ac674e, a single run; the signed record states provider docker and isolation "kernel". It authenticates the recorded messages, not that what the guest printed is true. Not established by this check: the bundle around the line, and for a session call that its session's chain is whole; plimsoll-attest verify checks a whole bundle

In that run the adapter checked on its order 4 times. Change the 4 to a 5 in a copy and check again:

$ ../../../plimsoll-attest verify-entry -pub harness.pub -line 13 bundle-altered.jsonl
plimsoll-attest: attest: broken bundle chain: the line's link signs other content

go run ./examples/adapter -verify docs/examples/adapter rebuilds every verdict from its evidence: "verified: 51 run records and 51 qualification statements, every verdict rebuilt from its evidence".

What this does not prove

A seal proves who sealed it, not that the contents are true. The vendor is my simulator and the ledger is its own account, so you can rebuild a verdict but not check it against a real robot company. Nothing on the page vouches for the signing key. The "kernel" isolation tier (docker under gVisor) is what plimsoll's server reports from its configuration and startup checks, not hardware attestation. The event log above is drawn for reading; the signed parts are the ledger, the robots and the reports.

The test isn't hard for current models. Opus's adapter passed all eight scenarios. Haiku's and Sonnet's failed only the overloaded vendor, by giving up before it recovered and saying so. The example shows the grading, not a leaderboard.

If you build adapters

  • Give every command an order number the vendor honors.
  • Let "I don't know" be a valid answer.
  • Judge the adapter by the vendor's state, not its report.
  • Run it where it can't reach your keys.
