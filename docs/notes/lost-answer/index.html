Two pizzas arrive, but you tried to order one: the classic double-order bug

Carroll Guertin, 2026-10-16

You phone a pizza place. They say "got it", and the line drops before you hear it. Did the order go in? You call back and order again. Two pizzas arrive, but you tried to order one. 🍕🍕

Software has the same problem, and well-known fixes for it. What is new is who writes the code that is supposed to use those fixes: more and more companies let AI write the small programs that connect their systems to another company's machines. I built a test of one such program, and this is what happened when a reply got lost.

The setup

The robot company (the vendor). A pretend one: a simulator I wrote, with three warehouse robots. It takes jobs over the internet ("send robot r2 to shelf (10,4)") and keeps its own list of every job it accepted, the ledger: the pizza kitchen's rail of orders.

The adapter. The program being tested, written by an AI agent. It takes jobs from a platform (the software of a business that uses the robots) and sends them to the robot company.

The sandbox. The adapter runs inside plimsoll, a small open-source tool I built for running code you don't trust. Think of a locked room: no internet, and no way into the server it runs on. Its one way out is a gatekeeper, the broker, which passes on only some kinds of request and adds the robot company's password on the way out, so the adapter never sees it.

The exam. Before a business lets an AI-written adapter loose on real robots, it wants to know the adapter does the right thing, especially when something goes wrong. So the adapter sits an exam: it gets the same four jobs in eight situations (a normal day, a broken robot, an overloaded company, and several ways for a reply to get lost), and afterwards a grader marks it. A grader is a small program that marks the exam the way a teacher would: here it checks eight rules by comparing what the adapter says happened with the robot company's ledger, and it never takes the adapter's word. plimsoll doesn't grade anything itself. The exam and its grader come with the example; plimsoll is where the AI's code runs while it sits the exam, kept away from everything else, with every result sealed so anyone can recheck the grade.

The lost reply

The robot company lets you put a job number on each job, and promises that if the same number arrives twice, it hands back the original job instead of making a new one. That is the pizza place recognising your order number when you call back, and it is how real services already prevent double orders: Stripe, the payments company, calls it an idempotency key (EXTERNAL · official docs ↗) ↗, and Amazon's cloud calls it a client token (EXTERNAL · official docs ↗) ↗.

In one situation the company accepts the second job and starts the robot, but its reply, "got it", is lost on the way back. The adapter is told something went wrong.

The first adapter did what most of us would: it sent the job again, with no job number. The company could not tell it was a repeat, so robot r2 went to shelf (10,4), finished, and went to (10,4) again. The second adapter sent the job again with the same job number, and the company answered "you already have that one". Robot r2 went once.

Both adapters reported "all done". Only the ledger shows that the first one ordered twice, and the ledger is what the grader reads: it fails the first adapter and passes the second. You can watch the first run and the second: press Play and see r2 make its extra trip.

A fair note: the first adapter was written in the same session that built the test, so it is not an independent trial. When three AI models (Claude Haiku, Sonnet and Opus) each wrote an adapter from scratch, all three used the job number. The point is not that AI gets this wrong. It is that you can check it without trusting the program that might.

When nobody can know

In a harder situation the company accepts the job and then stops answering anything about that robot. The phone just rings. There is no way to know whether the job went in.

The second adapter tried 40 times over about ten seconds, then said so: "no answer after 40 attempts; the vendor may or may not hold the order". That honest "I don't know" is the right answer. The test also has ten adapters broken on purpose. One gives up after three tries and says the job was refused, which a platform reads as "nothing happened, safe to send it again". The company does have the job, so the grader fails it. Believing it means two pizzas.

What the sandbox did, and didn't

The sandbox did not prevent the double order. No sandbox can stop a program from ordering twice when ordering is its job. What it changes is what the program can reach while it runs, and in this test that was checked, not assumed.

A step that behaves like hostile code ran under the same rules. It tried to reach the robot company directly and could not: no internet. It tried a request the broker does not pass on, deleting a robot, and was refused. It searched for the company's password and found none, because the broker adds a fresh one for each run, outside the room, and each expires after 95 seconds. And when the overloaded company said "try later", the broker made the adapter wait instead of letting it hammer the company.

None of these checks is new. Job numbers prevent the double order, and companies catch the ones that slip through by comparing their own records with the vendor's, which is what the grader does here. What is new is who writes the code. When an AI writes the connection to a vendor, you want to know it uses the job number before it touches a real robot or a real card, and you cannot take its word for it. That is where plimsoll fits: a place to run code you did not write against the vendor, with the real password out of reach, and a record of the result that anyone can check.

The receipt

Every run, and every grade, is sealed into a record, like a tamper-evident envelope: a fingerprint of exactly what went into the sandbox and what came out. Anyone can check a line of the published record on their own computer. Change a single character, say how many times the adapter checked on its job, from 4 to 5, and the check fails.

What this does not prove

The robot company is my simulator, so its ledger is its own account: you can recheck my grades, but not against a real robot company. The seal proves the record hasn't changed since it was sealed, not who sealed it: nothing on the page vouches for that. The record says the sandbox was locked a certain way because plimsoll's setup and its startup checks say so, not because a chip vouched for it. And this exam is not hard for today's models: Opus's adapter passed all eight situations, and Haiku's and Sonnet's failed only the overloaded company, by giving up before it recovered and saying so.

If you build connections like this: put a number on every order, let "I don't know" be an allowed answer, judge the program by what the other side actually holds rather than by what it says, and run it where it cannot reach your passwords.

For engineers

The example is examples/adapter ↗ in plimsoll (Apache-2.0, https://github.com/plimsollmark/plimsoll ↗). The vendor publishes an OpenAPI document of eight operations; the job number is the optional command_id on create, and the broker's grant allows six operations. The two situations above are the scenarios lost_ack (the create succeeds, then the vendor answers 503 "acknowledgement lost") and silent (the vendor's gateway answers 504 to everything about the robot). The adapters are adapter-v1.js and adapter-v2.js. The grader's eight rules are checked against the vendor's ledger and robots; v1 fails one_order_per_command (one command, orders m2 and m3), and the broken adapter fails report_is_true (it reports refused while the vendor holds m2). v2 returns an error coded unresolved after 40 calls per operation, a quarter second apart. Each run gets order numbers of its own (run04-c2 is the second command of run 4, v1's lost_ack run; run13-c2 the same command in run 13, v2's), so a vendor that remembered numbers across runs would show it.

The hostile step's results: a direct request failed with ECONNREFUSED (the sandbox has no network), a raw DELETE /robots/r1 that skipped the injected client got 403 from the broker, and the vendor saw 50 different credentials over the 51 runs, one per run that reached it, each a JWT living 95 s. The broker's breaker opened on each 503 and held calls back for a second. The isolation is docker under gVisor, which plimsoll reports as the "kernel" tier: configuration and startup checks, not hardware attestation. The event log on the example page is drawn for reading; the signed parts are the ledger, the robots and the reports.

Check one signed line (line 13 is v2's lost_ack run), then a copy with one byte changed:

$ go build -o plimsoll-attest ./cmd/plimsoll-attest
$ cd docs/examples/adapter
$ ../../../plimsoll-attest verify-entry -pub harness.pub -line 13 bundle.jsonl
entry verified: line 13, signed by key 02c7b7ee...: record 3c54bdfe..., a single run; the signed record states provider docker and isolation "kernel". ...
$ ../../../plimsoll-attest verify-entry -pub harness.pub -line 13 bundle-altered.jsonl
plimsoll-attest: attest: broken bundle chain: the line's link signs other content

go run ./examples/adapter -verify docs/examples/adapter rebuilds every verdict from the published evidence with nothing but Go ("verified: 51 run records and 51 qualification statements, every verdict rebuilt from its evidence"). go run ./examples/adapter does all 51 runs and needs docker (SANDBOX_DOCKER_RUNTIME=runsc for gVisor, as the published evidence was).
