Undoing ext4's fixes, one at a time: which tests notice?

Carroll Guertin · 2026-11-26 · every script, raw result and command is on this page

The idea, for anyone: when someone fixes a bug and adds a test, that test should fail if you undo the fix. If it still passes, it is not guarding that fix. So I took the 48 bug fixes in one big Linux pull, undid each one, and ran the tests.

What came back: 41 of the 48 could be undone on their own. For 6 of those, some test failed (the test is doing its job). For 1, the test kernel crashed part way through, which is also the tests noticing. For 34, every test still passed. 7 could not be undone alone, because later fixes changed the same lines.

The interesting one: a fix whose test claims to cover it, yet the test passed with the fix removed. It looked like a missing test. It was not: a later fix in the same pull prevents the same damage. Undo both, and the test fails at the exact line I predicted, in writing, before the run.

Credit first. Ted Ts'o, the ext4 maintainer, had already fixed both problems this page runs into: the two tests that fail at Linus's merge (ext4 dev commit 97f29574e12e, dated 19:13 UTC on 2026-11-25, two and a half hours before my first run) and a crash of the new tests when the kernel is built with CONFIG_USER_NS=y (ad592b92d677). Nothing here is a new bug report. The kernel code was right in both cases; what was missing was a test stub and a field in a test's fake superblock.

Words used on this page

ext4
A Linux filesystem, the default on many distributions: the code that lays files out on a disk.
KUnit
The Linux kernel's built-in unit test framework. Each test calls a small piece of kernel code directly and checks the answer, with no real disk. EXTERNAL · official docs ↗
kunit.py
KUnit's runner: it builds a test kernel, boots it, and reports each test as passed or failed. EXTERNAL · official docs ↗
UML (User Mode Linux)
The kernel built as an ordinary program, so the tests run on a laptop without a virtual machine. Every run here is 64-bit x86 UML.
A Fixes: tag
The line in a kernel commit message that names the commit whose bug it fixes. EXTERNAL · official docs ↗
Undoing (reverting) a fix
Here, always: at the pull's last commit, reverse the fix's changes outside the test files (fs/ext4/*-test.c) and keep the tests as they are. A plain git revert would also delete a test that arrived in the same commit as its fix.
Witnessed
Some test fails with the fix undone and passes with it in place. That test is a witness for the fix.
Passes both ways
Every test passes with the fix undone too. This does not mean the fix is untested: ext4's main regression suite is xfstests, which tests a real mounted filesystem and was not run here (EXTERNAL · project docs ↗). It means the KUnit tests did not catch that fix being undone, under this one configuration.
KASAN
The kernel's memory-error detector, a build option that turns an out-of-bounds access or a use after free into a report. EXTERNAL · official docs ↗
jbd2
The journaling layer ext4 sits on, in fs/jbd2/, a separate directory from fs/ext4/.
Kernel configuration
The list of options a kernel is built with. CONFIG_USER_NS turns on user namespaces (separate user id ranges, the thing containers use); kunit.py's --kconfig_add adds an option on top of the suite's own list, fs/ext4/.kunitconfig.

Why this pull

On 2026-11-24 Ted sent the ext4 pull for 7.4-rc5 (base 7475ea8b5861, which is v7.4-rc2, tip bae28a1b11f4, 94 commits, 41,197 added lines). Most of the new lines are KUnit tests; his message says they make it "safer to validate AI generated patches" (EXTERNAL · mailing list ↗). Linus merged it as 4dce97c6c265 and, replying to Ted, wrote that the test conflict resolutions looked right to him "but I didn't *run* any of them" (EXTERNAL · mailing list ↗).

That raises a question you can answer with a computer: do the new tests notice when the fixes they ship with are taken away?

The 2 failures at the merge are ext4_inode_test.inode_test_get_inode_loc_variants and ext4_inode_test.inode_test_write_and_sync_metadata. Linus's side of the merge had switched ext4_get_inode_loc_noio() to a non-atomic block lookup (d25c14b2d79e), and the merge kept that through a new wrapper, ext4_sb_find_get_block_nonatomic(). The pull's test replaces only the old lookup, ext4_sb_find_get_block(), with its fake buffer cache, so the fake is never asked and the function returns "try again" (-EAGAIN). Putting that one call back to the old lookup makes all 41 inode tests pass, which located the cause; Ted's actual fix adds the missing stub to the test instead (2 lines in fs/ext4/inode-test.c), which is the right fix: the code was correct.

2. Undoing each of the 48 fixes

The pull has 50 commits with a Fixes: line; one touches only test files and one changes only a comment, which leaves 48 that change code. For each, at the tip:

git diff FIX^ FIX -- . ':!fs/ext4/*-test.c' | git apply -R --3way
python3 tools/testing/kunit/kunit.py run --arch=um --kunitconfig=fs/ext4
  • 41 undid cleanly. 6 made some test fail. 1 (f62b22b69aef) made the kernel panic part way through the suite (342 tests pass, 220 are never reached). 34 left all 562 passing.
  • 7 could not be undone alone: a later commit of the same pull changed the same lines, so "the tip without this one fix" is not a well-defined tree.
  • Two of the 6 were caught by tests that name no bug: daa099ec5ce3 (orphan file size check) and ff06f373c1d7 (journal recovery on an incomplete fast commit) were caught by the pull's general coverage tests. The other 4 are caught by a test that says it covers them.
  • What the 34 are. Of the 34, only one (337c173f966c, next section) is a fix a test in the pull claims to cover. 6 are jbd2 fixes, outside fs/ext4/ entirely, and c966757ff80f is a bug in 32-bit kernels, which a 64-bit build cannot show. Five are memory-safety fixes, the most likely to hide from a build without KASAN, so they were rerun on a laptop with CONFIG_KASAN=y: the tip and each of the five undone still pass 562 of 562 with no KASAN report (KASAN summary).

Every job took about 7 seconds (an incremental rebuild plus the whole suite) on a 16-CPU cloud sandbox. The tool's verdicts are derived from each job's raw result file, which lists every test's status with and without the fix: all 48 result files and this table as JSON. One correction to the tool, made after this run: it labeled the crash "cannot run", the same words as a conflict; it now reports such a job as stopped part way, and the table says what happened.

3. Masked, not missing: 337c173f

The pull's last commit, bae28a1b11f4, adds migration tests and says in its message that they cover several fixes, among them "ext4: don't free the tmp_inode tree after a partial migration swap". That is 337c173f966c; the message cites it by its pre-rebase hash, 047061e6a6da, so searching the message for 337c173f finds nothing. Undo it, and all 11 migration tests still pass.

Reading the code first, without running anything: the test does check the outcome that fix protects. Line 1351 of fs/ext4/migrate-test.c, KUNIT_EXPECT_FALSE(test, migrate_was_freed(ctx, ext_idx_pblk)), asks whether the migrated inode's extent index block was freed after a failed swap, which is the bug in 337c173f's own message. But a later fix in the same pull, 6bda1a98b7ce (another author's; it carries no Fixes: line, so it is not one of the 48), empties the temporary inode's extent tree before anything can fail. With it in place, the call 337c173f skips frees nothing anyway. A belt where the braces are already on.

So the guess was masked: line 1351 should fail only when both are undone. The other guess, that no test reaches this bug, says line 1351 never fails. I wrote down, for each of five cases, which way line 1351 would go, and committed that before the run (prediction, cases; committed 23:02 UTC on 2026-11-25, first job 23:07 UTC, per the run's own log). Those commit times are from my private repository, so for the order you have my word, not a public timestamp; the laptop rerun below reproduces the outcome either way.

What no test at the tip can do is fail for 337c173f's absence alone, because 6bda1a98 makes it redundant there. Not run, so a reading only: on a tree that takes 337c173f without 6bda1a98 (a stable backport picked one at a time, say; both carry Cc: stable), 337c173f alone would decide line 1351.

The general lesson for anyone checking tests this way: "passes both ways" can mean a later fix is doing the same job. Undoing fixes that touch the same code in pairs, and watching the one line that names the bug, told the two apart in one run.

4. Rerun it on your laptop

You need Docker, Python 3 and about 3 GB of disk. The first run fetches the kernel history since 2026-11-01 from GitHub (633 MB) and two commits of Ted's tree from git.kernel.org, and builds the test kernel; later runs reuse both. On my laptop the first masking run, fetch and build included, took about 4 minutes.

curl -sLO https://plimsollmark.github.io/plimsoll/case-studies/ext4-witness/scripts/reproduce.sh
for f in setup.sh witness.py queues.py fixes.json; do
  curl -sLO https://plimsollmark.github.io/plimsoll/case-studies/ext4-witness/scripts/$f
done
sh reproduce.sh masking     # section 3: six jobs
sh reproduce.sh merge       # section 1, the suite's own config
sh reproduce.sh config      # section 1, both configs and Ted's dev tip
sh reproduce.sh fixes       # section 2: all 48

Each prints one line per job and leaves every result file and kunit.py log in ext4-witness-out/. These exact scripts were run that way before this page went up (sh reproduce.sh masking, on a laptop, 2026-11-26): line 1351 failed only with 337c173f and 6bda1a98 both undone, every other failed expectation matched the table in section 3, and the tip passed 562 of 562 (its summary, its result files).

  • witness.py: the program that runs each job (undo the fixes, run the suite, compare every test). Standard library Python only.
  • queues.py: the job lists for each section, every commit spelled out; fixes.json: the 48 fixes with titles and files.
  • setup.sh: the build tools and the two public fetches, inside the container.
  • reproduce.sh: runs the above in a Debian container pinned by digest.

The runs on this page were made in a 16-CPU cloud sandbox, driven by a small script of mine that creates the sandbox, copies witness.py and a queue in, and copies the results out. That script is specific to the cloud service and its billing and is left out; nothing in it changes a result. witness.py here is the version that ran last, changed only so its paths can be moved and ccache is optional.

Already rerun once, on a different machine. A second check, written separately from witness.py (its own undo and run commands), ran on a laptop: Debian bookworm's gcc 12, no ccache, a fresh clone. The tip passed 562 of 562 three times; the same 6 fixes were caught by the same tests; f62b22b69aef stopped at the same 342 with BUG: failure at fs/ext4/ext4_jbd2.c:36; 82e2a5743b6a conflicted the same way; undoing 6bda1a98 and 337c173f together failed lines 1327, 1328 and 1351 and nothing else. After the first build each run took 4 to 6 seconds; the whole rerun took under two minutes (summary, test-for-test comparison, every log, its .config).

What this shows, and what it does not

  • Shows: under UML, 64-bit, the suite's own configuration, which of the pull's 48 fixes the ext4 KUnit tests notice being undone, one at a time, with the test files kept. And that the one apparent miss among the fixes a test claims is a fix made redundant by a later one.
  • Does not show: that the 34 are untested (xfstests was not run, and most of them never claimed a KUnit test); anything about other configurations (KASAN only for five fixes; no lockdep, no QEMU, no other architecture); anything about the 7 that conflict; that the fixes are correct; or that tests like these validate AI-written patches in general.
  • About run records. I build plimsoll (INTERNAL · plimsoll site →), a sandbox for untrusted code that returns a run record with each run: SHA-256 digests binding the request and result bytes to the daemon's account of the run (EXTERNAL · source repo ↗; even there a record is the daemon's statement, never proof of what a machine actually ran). The runs on this page did not go through plimsoll and carry no run record. What you can check instead is every raw result file and log, the exact commits, and the rerun above, which gives the same answer test for test.
