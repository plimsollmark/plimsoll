# The example programs

Go programs, a shell recipe and a TypeScript example: what each shows, what it needs,
and the one to read if you only read one. Part of the [plimsoll README](../README.md).

`minimal`, `grant`, `daemon` and `advisor` need no docker, credentials or daemon you
start yourself. `oracle`, `wasm-controller`, `wasm-buck` and `adapter` need docker and
the images `make docker-images` builds. `providers` additionally uses any hosted or
gateway <dfn>*provider*</dfn>, a backend that runs the code, it has settings for, including paid services. `sessions` needs an
<dfn>*OpenShell*</dfn> gateway, NVIDIA's server for creating sandboxes.

`agentsandbox`, `capsule` and `sbom` rebuild pages from recorded evidence offline.
Run Go examples from the repository root; `capsule` (Go 1.27) and `sbom` have their
own modules, so their commands change directory first. The pull-request [receipt (INTERNAL · glossary →)](trainers/glossary.html#receipt)
recipe needs docker, [gVisor (INTERNAL · glossary →)](trainers/glossary.html#gvisor) and the containerd image store, which stores the exact
image descriptions it records. The TypeScript example uses npm from its own directory.

| Command | What it shows |
|---|---|
| `go run ./examples/minimal` | One snippet, its result, and the <dfn>*isolation tier*</dfn> the run reports: how strong the wall around it was. |
| `go run ./examples/grant` | How a <dfn>*grant*</dfn>, one run's permission to call listed routes of an API, works: a permitted route, a refused one, the same refusal when the <dfn>*guest*</dfn> (the code in the sandbox) skips the client plimsoll gave it and calls out by hand, the same request succeeding in a separate run whose grant lists it, and a search for the credential that finds nothing. |
| `go run ./examples/daemon` | The service: `plimsolld`, the plimsoll server, started with a real file of callers, called by the Go client, refusing a <dfn>*floor*</dfn> (a minimum tier) it cannot meet and refusing a wrong token. Each refusal is checked for its specific error: `ErrInsufficientIsolation`, and `unauthenticated` from <dfn>*Connect*</dfn>, the RPC library plimsolld speaks. A request that merely failed is not proof the protection fired. |
| `go run ./examples/advisor` | The efficiency advisor, which reads the API calls a run made: one question asked twice of a fake inventory API. First as a loop with one request per item (13 requests, and a `fan_out` finding naming the route, already allowed by the grant, that returns the whole list), then as the advice suggests (1 request, no findings). Same answer both times. |
| `go run ./examples/oracle` | The <dfn>*physics oracle*</dfn>, which tests code by what it makes a simulation do. An agent-written <dfn>*controller*</dfn> (a program that decides at every <dfn>*tick*</dfn>, one 10 ms step of the simulation, how to push the cart) is the only file of a project run. It runs against a <dfn>*cart-pole*</dfn> simulator (a cart on a rail with a pole hinged on top, to be kept upright), compiled to <dfn>*WebAssembly*</dfn> (a portable bytecode) and built into the module image. The runner, a program also built into the image, runs the controller as a separate process, records its <dfn>*trajectory*</dfn> (every state at every tick), and hashes that into a <dfn>*fingerprint*</dfn>: a SHA-256 hash, so equal fingerprints mean identical numbers. The accepted controller runs twice (one fingerprint), the agent's draft once (another, and it drops the pole at 5.96 s). The page it writes, live: [the physics oracle](https://plimsollmark.github.io/plimsoll/examples/oracle/index.html), which replays the recorded runs (source: `docs/examples/oracle/index.html`). |
| `go run ./examples/providers` | The oracle's run on every provider the machine can reach, each built the way plimsolld builds it: the same accepted controller, runner and cart-pole simulator, sent as ordinary project files so no special image is needed, and each provider proven ready before its run counts. The page it writes, live: [same run, different sandboxes](https://plimsollmark.github.io/plimsoll/examples/providers/index.html), shows each provider's isolation tier, Node version and fingerprint beside the one the oracle page published (source: `docs/examples/providers/index.html`). The rows for <dfn>*E2B*</dfn> and <dfn>*Docker Cloud Sandboxes*</dfn>, two hosted services that run each request in its own small virtual machine, need their credentials and are billed; the OpenShell row needs a gateway. |
| `go run ./examples/fanout -verify` | One job fanned out to many sandboxes at once and fanned back in: a picture of the Mandelbrot set cut into 256 tiles, each computed twice in two different rooms (a room is one daemon serving one provider at one isolation tier), reached through [placement](placement.md) as one pool. Every call is signed into one bundle, and the page is rendered from that bundle alone: the two answers for every tile must match byte for byte, since the tile program uses only arithmetic that IEEE 754 makes exact in every JavaScript engine. `-verify` checks the signatures, the chain, each record against its request and answer, the agreement, and that the page and picture are what the bundle renders, and starts no sandbox. The page, live: [one job, every sandbox](https://plimsollmark.github.io/plimsoll/examples/fanout/index.html) (source: `docs/examples/fanout/index.html`). Running it again needs a daemon per room (`-daemons FILE`); the E2B and Docker Cloud rooms are billed. |
| `go run ./examples/wasm-controller` | A controller in a compiled language. A cart-pole swing-up controller (it swings the pole up from hanging, then balances it) is written in C and sent as a file of a project run, whose first step compiles it to WebAssembly inside the sandbox (`plimsoll/sandbox-wasm-cc`). The image's generic trial runner runs it against the same simulator on four scenarios, through a small Node adapter that gives the compiled module no outside functions to call. Two runs give one hash of the compiled module and one fingerprint per scenario, with the pole up within 2.5 s in each. Two more runs compare it with the same <dfn>*control law*</dfn> (the formula the controller applies at each tick) in JavaScript, and with the same C built against Node's `Math.cos`. The page it writes, live: [a controller in C, checked by its trajectory](https://plimsollmark.github.io/plimsoll/examples/wasm-controller/index.html), replays the swing-up and shows, tick by tick, that the C and JavaScript records differ only in the last bits of a few force values, while the motion is bit-identical (source: `docs/examples/wasm-controller/index.html`). Its [README](../examples/wasm-controller/README.md) says why the fingerprints differ from the JavaScript version's (the last bit of `cos`) and what the example does not prove. |
| `go run ./examples/wasm-buck` | A controller in C for a <dfn>*buck converter*</dfn>, a power supply that steps a voltage down by switching it on and off many times a second. It uses the same adapter, runner and compile step, and holds 5 V out from 10 to 16 V in through a load that halves at an unknown moment. Two C runs and one JavaScript run of the same control law give one module hash, and in every scenario the C trajectory equals the JavaScript one byte for byte: the law calls no library function, and the compiler is told not to merge a multiply and an add into one step (which would round differently). The page it writes, live: [a buck converter controller in C](https://plimsollmark.github.io/plimsoll/examples/wasm-buck/index.html), charts, tick by tick, the output voltage, the current through the converter's coil (inductor current) and the share of each cycle its switch is on (duty cycle) (source: `docs/examples/wasm-buck/index.html`). Its [README](../examples/wasm-buck/README.md) says what it does not prove. |
| `go run ./examples/sessions` | A <dfn>*session*</dfn>, one sandbox kept for many calls ([sessions.md](sessions.md)), on an OpenShell sandbox through plimsolld. A <dfn>*harness*</dfn>, a program outside the daemon, signs every call's <dfn>*run record*</dfn>, the daemon's statement of what was sent, what came back and where it ran ([run-records.md](run-records.md)). The calls: a project whose test fails, a snippet that patches the file in place, the test passing without the files being sent again, a snippet that leaves a background process running, and a snippet that finds it gone. The signed set of records is verified, then refused once with one call dropped and once with one byte of output changed. The page it writes, live: [one sandbox, five calls](https://plimsollmark.github.io/plimsoll/examples/sessions/index.html), with the signed set and the harness's public key beside it (source: `docs/examples/sessions/`). Needs a gateway and the five `SANDBOX_OPENSHELL_*` settings; spends nothing. |
| `NEBIUS_API_KEY=... go run ./examples/nemotron-agent` | A coding agent on an NVIDIA Nemotron model served by Nebius Token Factory, whose single callable function, `run_code`, runs code in a plimsoll session behind gVisor: the model writes code, the code runs, the real output goes back, it fixes and reruns, and every run leaves a signed run record in a bundle the harness writes beside the page. The page shows the conversation, each run with its record, and the verifier accepting the bundle; its test runs the loop against a scripted model and an in-memory daemon and spends nothing. Needs docker with gVisor, the images from `make docker-images`, and a Token Factory key in the environment; the model calls cost cents. |
| `cd examples/capsule && go run .` | Each call of the sessions example's signed bundle, once the `attest` verifier accepted it, stated as an Agent Action Capsule and checked by that project's Go and Python verifiers. Its own Go module, because the capsule code needs Go 1.27 and dependencies plimsoll does not take on. |
| `go run ./examples/adapter` | An AI-written adapter, code that connects a platform to a device vendor's API, tried against a simulated robot fleet. The host checks its reported answers against the vendor's ledger under faults, lost answers and refusals, and signs the qualification verdict, the result of those checks, with a verdict per requirement ID of a requirements file each statement names by its SHA-256 fingerprint; `-verify docs/examples/adapter -adapter FILE` answers offline whether that exact file qualified. Needs docker. [INTERNAL · adapter contract →](../examples/adapter/contract/CONTRACT.md); [INTERNAL · recorded fleet replay →](examples/adapter/index.html). |
| `cd examples/sbom && go run .` | Signed run records converted to CycloneDX 1.6 software bills of materials, ingredients labels carrying the run's evidence. Offline conversion and checking; no new sandbox. [INTERNAL · converter guide →](../examples/sbom/README.md); [INTERNAL · interactive receipt checks →](examples/sbom/index.html). |
| `go run ./examples/agentsandbox` | Rebuilds the evidence page from recorded Kubernetes <dfn>*agent-sandbox*</dfn> runs, the Kubernetes component that lends ready pods from a pool: the same two requests under gVisor and under <dfn>*Kata Containers*</dfn>, a runtime that starts each pod in a small virtual machine of its own, compared with docker and Docker Cloud. The rooms it compares are a list in `rooms.json` beside the page. It checks the signed records and refuses altered evidence; it starts no cluster. [INTERNAL · recorded runs, comparison and refusals →](examples/agentsandbox/index.html); [INTERNAL · live deployment guide →](agentsandbox.md). |
| `go run ./examples/fanout-cartpole -verify` | What `fanout` does, with a batch of grading as the job: 64 cart-pole controllers (linear state-feedback laws on a grid of two gains, made by hand), each tried from 4 starting angles, every trial run twice in two different rooms through [placement](placement.md) and signed into one bundle. The trial program uses only arithmetic IEEE 754 makes exact and fixed polynomials for sine and cosine, so both answers must match byte for byte, a fingerprint of the whole trajectory included. The page is a scoreboard of how many starting angles each controller balanced from. `-verify` checks the bundle and that the page is what it renders, and starts no sandbox. Shares its engine with `fanout` ([INTERNAL · fanjob →](../examples/internal/fanjob/fanjob.go)). The page: [grading a batch of controllers](https://plimsollmark.github.io/plimsoll/examples/fanout-cartpole/index.html) (source: `docs/examples/fanout-cartpole/index.html`). |
| `go run ./examples/agent-session` | Where a coding agent's code ran, per coding session: a hook for Claude Code or Codex makes every run through plimsoll's [MCP (INTERNAL · glossary →)](trainers/glossary.html#mcp) server carry the session's ID as its trace, which the server signs into the run's receipt, and this command gathers the session's runs from the receipts into one signed statement (each run's tier, provider and record, and the weakest tier); `-check` confirms a statement against the receipts. It lists the runs that carried the trace, not code the agent ran elsewhere. [INTERNAL · hook and statement →](../examples/agent-session/README.md) |
| `go run ./examples/squeeze -verify` | The squeeze test, from Bertran, Roth and Wu's paper "What Fits (Into Few Tokens) Doesn't Overfit": did an AI loop that graded itself on the same practice tests every round learn the job, or memorize the test? Squeeze what it learned into a recipe of about 32 tokens (the units a language model reads and writes), let fresh agents rebuild from the recipe alone, and compare their scores with the loop's on the loop's own practice tests. Ported from the did-it-learn hackathon entry's drone course: each rebuild is the caller's model in a fresh session that never holds the simulator (it practices through a separate run that answers with flight results), every controller is graded in runs of its own on two sealed sets of flights, and a leak scan over the signed bundle checks that no rebuild's sandbox held a sealed seed, the loop's controller or the simulator. The published run grades the hackathon's own 96 controllers and calls no model; `-verify` checks it and starts no sandbox. The page tells the story with the recipes verbatim: [the squeeze test](https://plimsollmark.github.io/plimsoll/examples/squeeze/index.html) (source: `docs/examples/squeeze/index.html`); its [README](../examples/squeeze/README.md) says what the test cannot tell you. Running it again needs docker with gVisor; making rebuilds needs a model key and a token budget. |
| `go run ./examples/ship-scan` | The ship scan end to end, on the WASM provider (no docker, no network, no credentials): a toy harness and three made-up seeds, a withheld set built the way docs/ship-scan.md recommends (the harness's files refused, the seeds audited, so an agent cannot use a refusal to test a guess), and five calls: a clean controller runs; the simulator shipped as it is, edited, and packed in a .tar.gz is refused before any code runs, marked as never handed to a sandbox, so the caller may fix it and send it again; a seed in an agent's code runs and only the operator's log names it. The same set scans two folders offline. `-verify` checks every claim against the published evidence, recomputes the clean call's run record, and the tests check that no seed or simulator line reaches an answer, a log line or the page. [INTERNAL · the ship scan, five calls →](https://plimsollmark.github.io/plimsoll/examples/ship-scan/index.html) |
| `go run ./examples/verifiers` | Prime Intellect's verifiers, the Python library for the environments AI models are trained and tested in, on plimsoll through the Python client's runtime plugin: every command, read and write of an unmodified verifiers task is one call of a plimsoll session, and every call's run record goes to a log that is rechecked afterwards, by the Python client and by a Go checker. `examples/grant` is the one to read if you only read one. After each step it prints the
run's `CallTrace`: the list of API calls the <dfn>*broker*</dfn> made for the code (the
broker is the part of plimsoll that makes those calls and holds the credential). The list
records only the route, the status, the sizes and the time taken, never the data, and the
efficiency advisor and the audit log are built from it:

```
1. a route the grant lists
   guest | ok: Engineering 46600000
   trace | #1 GET /v1/employees/*/comp -> 200, 0B in 39B out, 1ms

3. the same forbidden route, bypassing the client
   guest | broker answered: 403 forbidden by sandbox capability allowlist
   trace | 0 call(s), 1 denied by policy, 0 shed for backpressure, 0 dropped

4. the same request, in a run handed a separate grant that lists the route
   guest | ok: {"ssn":"000-00-0000"}
   trace | #1 GET /v1/employees/*/ssn -> 200, 0B in 21B out, 1ms
```

Scenes 3 and 4 send the identical request. The guest did not change and the API did not
change; the run was handed a different grant, and the grant is what decides.

Note what the list holds: the route pattern the request matched, such as
`/v1/employees/*/comp`, never the exact path that was requested. `CallRow` has no field
for a path, query, body or credential, so none can be recorded by accident.
