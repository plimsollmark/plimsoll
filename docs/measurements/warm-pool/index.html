Warm pool: never-used containers against a cold start

Whether a pool of locked-down containers that no code has touched, each claimed once and removed after, takes the container start off the path of a session's first call, and of a single call that asks for one (SANDBOX_SESSION_POOL; the terms session, cell and relay are defined in the sessions guide (EXTERNAL · source repo ↗)). The page has five parts: one call through the daemon (prefer_warm), the newest; the pool as built, the language hints that steer it, the same pool on OpenShell, and the probe that came first. The probe was measured 2026-10-02 07:51 PDT on a laptop, docker 29.1.3, image node:22-alpine, the docker provider's lockdown flags, 20 samples per bar, a node -e snippet as the call. A laptop number, not a product number: what carries over is the ratio and the breakdown, not the milliseconds.

The one-call path through the daemon (2026-10-29)

A Run, the daemon's call that runs code once in a sandbox of its own, may now carry a cell (INTERNAL · glossary →), code for a Python or JavaScript interpreter whose final value is printed, and ask for prefer_warm: the daemon then runs it in a pool member that is already waiting, a sandbox no code has touched with both interpreters running, and deletes the member after the one call. With no member free it runs the cell in a sandbox made for it, as it does without the flag (a miss: the call still runs, only slower). The answer's warm says which path ran. This section times that call end to end, as a caller sees it: onecall/main.go builds plimsolld from the checkout, starts it with the docker provider (or, for the OpenShell set, the openshell provider and a local OpenShell gateway, v0.1.2, with its docker driver), image plimsoll/sandbox-python:latest and a pool of 1 (SANDBOX_SESSION_POOL), and calls it over loopback (the machine's own network interface) with the Go client, which checks every answer's run record (INTERNAL · glossary →). The cell is 6 * 7; 17 samples per bar, each call preceded by an untimed 5.2 s pause so the pool has made its next member; the calls of a repetition run in the same order, so a change in the machine's load reaches every bar alike.

Six calls per language. One call, warm: a Run with prefer_warm, served by the waiting member. Session: open + cell: the same work as three calls, what the clients did before the daemon took the path over: a session opened warm-only (it is handed the waiting member or refused), one cell, then the close, which is not in the bar (the table has it). Fresh: the Run without prefer_warm, in a sandbox made for it. Miss: a Run with prefer_warm sent as soon as another such Run has taken the only member, while the pool is still making the next one, so it runs fresh. Fresh and miss are each measured twice, because a fresh run on docker first re-runs the provider's Preflight (INTERNAL · glossary →), its checks of the docker daemon, the runtime and the images, whenever the last one is 5 s old or more, and a warm call never does: Preflight due is the call as it comes after the pause, Preflight cached the same call sent right after a GET /readyz (untimed), which re-runs it. A caller whose calls are seconds apart on a quiet daemon sees the first; a busy daemon, where some fresh run or readiness check ran in the last 5 s, the second.

What these numbers do not show:

  • Another machine or a network. One laptop (linux/amd64, 24 CPUs, 18 GiB memory, go1.26.10), docker 29.1.3 on the same machine as the daemon and the client, so no network lies between them.
  • A workload. The cell does almost nothing, so the bars are the path's own cost, not a program's run time.
  • Bursts. The pool held 1 member and the calls came 5.2 s apart; more calls at once than the pool holds, or calls faster than it refills, turn warm calls into misses. The miss was measured only as the second of two calls in a row.
  • The machine's work. A warm call still costs a sandbox's start and removal; the pool makes them off the caller's path. What a waiting member holds in memory is measured in the sections below, not here.
  • The wall clock. This laptop's clock stepped back about a second several times during the sets; the samples are timed on the monotonic clock, which such a step does not move.

Built: the pool with interpreters attached (2026-10-02)

Each never-used member gets an interpreter started and its relay attached for every language the image runs, and OpenSession hands one over. Measured 2026-10-02 with pooled/main.go against the provider directly (not through plimsolld), image plimsoll/sandbox-python:latest, 10 samples per bar, 3 s between samples so the pool refills, a cell of 6 * 7. What made the first measurement slow: OpenSession re-ran the docker Preflight, which re-runs once its result is 5 seconds old, before claiming. A claim now skips it: the member was verified when it was made and is read back before every call, and it must match the execution state the last Preflight verified. With that, claiming takes under a millisecond and the time is the first cell's. The cost is memory: the interpreters a waiting member holds count inside its session's memory limit, including the language a session never uses.

Every hinted open got a warm member (a cold open is about 740 ms). Its first cell answered in 31 to 53 ms, above the 18 to 22 ms of the pooled run above; that gap was not investigated. A hint changes latency, never behavior: a cell in a language the member did not warm still runs, starting its interpreter on first use, and a session without a hint counts as wanting every language. Hints move members between sets and never add any, so SANDBOX_SESSION_POOL still bounds the memory.

Cold run todayPool claimPool claim + read-back

"Cold run" is today's path: docker run --rm of the snippet. "Pool claim" is docker exec of the same snippet into a pre-started, never-used member. "Read-back" adds the docker inspect a session already makes before every call; a pool would make it at claim.

Where a claim's time goes

docker exec of trueNode starting and printing

Most of what remains is the docker exec round trip and Node starting. A warm session cell takes 14 to 15 ms on this laptop because its relay is already attached and its interpreter already running (measured 2026-10-01); a pool member could be prepared the same way, which is what the pool as built (above) does.

What it costs

  • Memory held while idle: about 17 MiB per member under gVisor (its Sentry), under 1 MiB under runc. A pool of 8 under gVisor holds about 137 MiB, which SANDBOX_TOTAL_MEMORY_MB would have to count.
  • Restocking, off the call's path: starting a member takes 133 ms (runc) and 157 ms (gVisor); removing one 98 and 120 ms.
  • No clone caveats: every member boots on its own, and none is ever handed to a second call.

The data and how to rerun it

Raw samples beside this page: pass-2.json and pass-3.json (the probe), pooled-runc.json and pooled-runsc.json (the pool as built), hints-runc.json (language hints), openshell.json (the pool on OpenShell), onecall-runc.json, onecall-runsc.json, onecall-openshell.json, onecall-runc-repeat.json (one call through the daemon). exec-split.json holds two medians per runtime timed by hand (docker exec of true, and of the snippet); no program reproduces it. The programs are in measurements/warm-pool (EXTERNAL · source repo ↗). From a checkout, with the images make docker-images builds (and gVisor installed for the runsc runs):

python3 measurements/warm-pool/probe.py 20 docs/measurements/warm-pool/pass-2.json
go run ./measurements/warm-pool/pooled                  # runc
go run ./measurements/warm-pool/pooled -runtime runsc   # gVisor
go run ./measurements/warm-pool/hints
go run ./measurements/warm-pool/openshell                # SANDBOX_OPENSHELL_* naming a gateway
go run ./measurements/warm-pool/onecall                  # runc, through plimsolld
go run ./measurements/warm-pool/onecall -runtime runsc   # gVisor
go run ./measurements/warm-pool/onecall -tag repeat      # runc again, a second file
go run ./measurements/warm-pool/onecall -provider openshell  # SANDBOX_OPENSHELL_* naming a gateway
python3 measurements/warm-pool/report.py

Your numbers will differ from these: they are one laptop's. What should carry over is the ratio between a pool and a cold start, and where the time goes.
