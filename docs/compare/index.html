Self-hosted alternatives to E2B for AI-agent code, compared

You want an agent to run code it wrote, on machines you control, without trusting that code. This page compares the projects people find when they look for that: E2B self-hosted (Embed), Tencent Cube Sandbox, microsandbox, NVIDIA OpenShell, Kubernetes agent-sandbox, Beam (beta9), Docker Sandboxes (sbx), Temps, PandaStack, DifySandbox, Daytona, Northflank (bring your own cloud), and plimsoll. Every cell links to the page it came from, read on 2026-10-11.

Who wrote this. plimsoll's maintainer, so read it as one vendor's comparison. To keep it fair: each fact comes from the project's own documentation, README, license or release list, never from another comparison article; a fact found only in a project's marketing is marked (vendor claim); and plimsoll's weak points have their own section below. Terms used

microVM
A small virtual machine started per sandbox. The code gets its own Linux kernel, and the processor's virtualization keeps it apart from the host (Firecracker, libkrun, Cloud Hypervisor and RustVMM are programs that run them).
gVisor
A kernel written in Go that runs between a container and the host's kernel and answers the container's system calls itself, so the code never talks to the host kernel directly.
runc, plain container
Docker's default: the code shares the host's kernel, kept apart by Linux namespaces and cgroups. The weakest of the three for code you did not write.
KVM
The Linux kernel's built-in virtualization. MicroVMs need it, which rules out most cloud VMs that do not allow nested virtualization.
Outside-API keys
Where the password for an outside service (a database, a payments API) lives while agent-written code calls it. "Outside" means the code sees a stand-in and a proxy outside the sandbox adds the real key, so code that leaks what it holds leaks nothing.
seccomp, Landlock, chroot
Linux features that narrow what a process may do: which system calls it may make, which files it may touch, and which directory it sees as the root.
eBPF
Small programs loaded into the Linux kernel; here they filter a sandbox's network traffic.
CIDR
A way to write a range of IP addresses, such as 10.0.0.0/8.
RuntimeClass, NetworkPolicy
Kubernetes settings: which runtime a pod runs under (gVisor, Kata, plain containers), and which network traffic it may send.
One client, several backends
Whether the same code in your app can send runs to more than one place (your own machine, a hosted service) by changing configuration rather than code.

Pick by what you need

  • E2B's API, on your own hardware: E2B Embed (one Linux machine), or Tencent Cube Sandbox, which accepts E2B's SDK.
  • A microVM on a developer's laptop: microsandbox (a library, no server) or Docker Sandboxes (a CLI, not open source).
  • You already run Kubernetes: Kubernetes agent-sandbox with a gVisor or Kata RuntimeClass, Beam's beta9, or OpenShell's Helm chart.
  • Network off unless allowed: OpenShell and plimsoll deny it by default, and Docker Sandboxes' default mode allows only common development sites. E2B, microsandbox, Beam, PandaStack and DifySandbox start with the internet on.
  • One integration across several vendors and your own machine: plimsoll is built for that (Docker with or without gVisor, OpenShell, E2B, Docker Cloud Sandboxes), and every run states which isolation it ran behind. E2B's SDK also reaches Cube Sandbox, because Cube copies E2B's API.

Where plimsoll is weaker

  • It is new. First public release 2026-09-10, one maintainer, few users. The others above with thousands of stars have far more people running them.
  • No microVM of its own. Self-hosted, its strongest boundary is gVisor (it reports that as the kernel tier). The VM tier comes only from E2B or Docker Cloud Sandboxes, which bill by the second. If you need a microVM on your own hardware today, E2B Embed, Cube Sandbox, microsandbox or PandaStack give you one.
  • gVisor costs time. On one machine, a one-file TypeScript compile-and-run took 4.1 s under gVisor against 1.95 s as a plain container (median of 20, 2026-09-29; measurement ↗).
  • Before 1.0, versions move together. v0.21.0 changed the protocol, so a 0.20 client and a 0.21 daemon refuse each other; upgrade both.
  • No Kubernetes deployment of its own. It runs as one binary beside Docker, or in front of a service that runs the sandboxes.

Hosted only, not self-hostable

  • Modal Sandboxes: gVisor or VMs; secrets as environment variables in the sandbox; no self-hosting offered. modal.com ↗
  • Vercel Sandbox: Firecracker microVM; the SDK is Apache-2.0 but the service runs on Vercel. vercel.com ↗
  • Cloudflare Sandbox: A microVM per container instance on Cloudflare; Workers Paid plan. developers.cloudflare.com ↗

Out-of-date claims in other comparisons

  • Daytona is no longer open source (2026-06-11). Articles from before June call it AGPL and self-hostable. daytona.io ↗
  • E2B's self-hosting is now Embed: one Linux machine by Docker Compose, Terraform or Kubernetes, no license key. Older articles describe a Nomad setup on GCP. github.com ↗
  • Kubernetes agent-sandbox is at v1.0.6 with a v1beta1 API, not alpha. github.com ↗
  • Two repositories moved: e2b-dev/infra is e2b-dev/runtime, and microsandbox is superradcompany/microsandbox. github.com ↗
