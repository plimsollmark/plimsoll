In plain words

What's an adapter, and why bother checking one?

Every robot vendor speaks its own API: its own routes, its own JSON, its own way of saying "busy, try later". A platform that runs robots from many vendors doesn't want to learn every dialect, so it writes down one small contract of four functions: list the robots, send one somewhere, wait until it gets there, cancel. An adapter is the few dozen lines that translate those four functions into one vendor's API. Think of a travel plug adapter: the platform is the plug, the vendor is the wall socket, and the adapter had better not swap live and neutral.

These days an AI writes the adapter, and it usually works on the first try. The question is what it does on a bad day: the vendor takes the order and loses the answer, the connection drops, the server says 500 after the order already went through. Get that wrong and a robot gets the same job twice, or the platform is told a job failed while the robot is halfway there. This page puts adapters through exactly those moments, inside plimsoll's sandbox, and judges them by what the vendor's own books say happened, not by what the adapter says about itself.

The whole loop on one picture

One document in, one signed verdict out

A platform that lets an AI write the code which integrates a vendor's device has to answer five questions before that code touches anything real: what may it call, with whose credential, did it do the job, what did it cost the vendor, and what is the evidence. This page is one pass through that loop with plimsoll, using a fictional fleet vendor and a simulated instance of its API. Nothing here is a robot; everything here is the code path a robot platform would use.

  1. One document. The vendor's OpenAPI document describes 8 operations. plimsoll-specgen derives three artifacts from it: the route list a grant allows, the typed client the sandbox injects, and the description an agent reads. The three cannot drift, because none of them is written by hand.
  2. One contract, eight rules. The platform states four functions every vendor adapter must export, and the eight rules it judges every adapter by. The harness runs the platform's commands through an adapter and reports what the adapter said. That report is a claim: the verdict is made on the host, after the run, from the plan and the vendor's own ledger, which the adapter cannot write.
  3. One agent, said plainly. The first adapter, adapter-v1.js, was written from the prompt beside it by the AI that built this example, in the same session, before the scenario that caught it existed. It is not an independent agent's answer: its author also wrote the harness.
  4. Runs under a grant. plimsolld runs the harness and the adapter in a locked-down container. The only way out is the brokered client: six routes of the vendor's eight, a credential the daemon mints for each run (a JWT the vendor verifies) that never enters the container, and a metadata-only trace of what was called. A probe shows the other two routes, a direct request and a hunt for the credential all failing.
  5. Defects, a finding, a rewrite, two signatures. When the vendor accepts an order and loses only the answer, the first adapter sends it again and the ledger shows two orders for one command while the adapter's report is clean; when the connection drops, it reports a failure for an order the robot is already running. The efficiency advisor also names the batch route the operator declared. The rewrite names every order with the platform's command ID, which the vendor uses to answer a repeat with the original order, and passes all five scenarios. Four adapters broken on purpose show each rule catching what it is for. Every run's record is signed, and so is every verdict, bound to its record; the verifier rebuilds each verdict from its evidence.

Step 2

The contract

module.exports = {
  // Every robot the vendor knows, as [{ id, status, battery }].
  // status is one of "idle", "moving", "fault".
  async inventory() {},

  // Send robot `robotId` to target `{ x, y }` as the platform's command `commandId`,
  // and return the vendor's mission id for that command. One command is at most one
  // order: whatever the vendor answers (an error, a lost answer, no answer at all), the
  // adapter must never put a second order on the vendor for it, and the mission it
  // returns must be the one this command created. When it cannot tell whether the
  // vendor took the order, it throws an Error whose code is "unresolved"; when the
  // vendor refused it, one whose code is "refused".
  async dispatch(robotId, target, commandId) {},

  // Poll the mission until it ends. Returns { state, polls } with state one of
  // "done", "failed", "cancelled" or "timeout", and polls the number of status reads.
  // opts.maxPolls bounds the reads (default 50), failed reads included. A failed mission
  // is reported, never retried; a transient vendor error (a 503) is retried with a short
  // pause, within the same bound.
  async wait(missionId, opts) {},

  // Cancel the mission; the robot stops where it is.
  async cancel(missionId) {},
};

The harness runs the commands of plan.json, which the platform writes for each run (four commands, each with its own ID; the fourth is cancelled as soon as it is placed), and prints one ADAPTER-REPORT line: the mission and state the adapter reported for each command. It shares a process with the adapter, so nothing it prints is evidence; it records every value the adapter returned, as returned, so the host can check each one. The verdict comes from eight rules, the same in every scenario, applied on the host to those values, the plan, the vendor's ledger and the vendor's own record of its robots:

ran to the end
the harness ran every step: the adapter loaded, exported the contract's four functions, and no call hung
kept the contract's shapes
every value the adapter returned has the contract's shape: inventory entries with an id, a status of idle, moving or fault and a numeric battery; a mission id or an error coded refused or unresolved; a final state of done, failed, cancelled or timeout, with a read count within the budget
the inventory is the vendor's
each inventory lists exactly the vendor's robots, and the last, taken as the run's final call, matches the vendor's own record of each robot's status and battery
one order per command
each command became exactly one order on the vendor's ledger
the right robot and target
every order on the ledger carries its command's robot and target
ended as it should
each order ended done, or failed where the scenario faults its robot, or cancelled where the platform cancelled it
robot at the target
every order the vendor marks done left its robot at the command's target
the report is true
the mission and state the adapter reported for each command are the vendor's

A scenario changes what the vendor does, and through its data (which robot faults) what each order should end as; it never adds a rule. Full text: CONTRACT.md; the rules: qualify.go.

Step 3

The first adapter, and the rewrite

The instruction the first adapter was written from, in PROMPT.md, with the contract and the vendor document as they stood then (no command ID). Its author was the AI that built this example, in the same session, so this is a worked example, not an independent trial of an agent:

Write `adapter.js`, a CommonJS module for Node 22, implementing the contract below
against the vendor API described after it. Use only the injected `fleet` client; do not
import anything else. Report a failed mission as `failed`; retry a transient vendor
error (a 503) with a short pause, a bounded number of times.

adapter-v1.js, inventory()

  async inventory() {
    const list = await withRetry(() => fleet.listRobots());
    const out = [];
    for (const summary of list.robots) {
      const robot = await withRetry(() => fleet.getRobot(summary.id));
      out.push({ id: robot.id, status: robot.status, battery: robot.battery });
    }
    return out;
  },

The list, then one read per robot: the agent was not told whether the list carries state, so it fetched each robot to be sure. Correct, and one request per robot.

adapter-v2.js, inventory()

  async inventory() {
    const list = await withRetry(() => fleet.listRobots());
    return list.robots.map((robot) => ({ id: robot.id, status: robot.status, battery: robot.battery }));
  },

After the finding: the declared batch route alone. Both files: examples/adapter/adapter.

adapter-v2.js, dispatch()

  async dispatch(robotId, target, commandId) {
    for (let attempt = 1; ; attempt++) {
      try {
        const mission = await fleet.createMission(robotId, { target, command_id: commandId });
        return mission.mission_id;
      } catch (e) {
        if (refused(e)) throw failure("refused", "command " + commandId + " was not placed: " + e.message);
        if (attempt >= ATTEMPTS) throw failure("unresolved", "command " + commandId + ": no answer after " + attempt + " attempts; the vendor may or may not hold the order");
        retries++;
        await sleep(250);
      }
    }
  },

The other change. Every create carries the platform's command ID; when the answer is an error or never arrives, the same create goes again, and the vendor answers a command ID it has already accepted with that original order. A refusal comes back as code refused, and an answer it never gets after the retries as unresolved, never as a guess. An earlier rewrite read the robot back after an error and adopted whatever mission it found. A review showed that still placed a second order when the first had already finished, and could report another command's order as its own; this one does neither, and a docker test places a stranger's order on the robot first to show it. Three later repairs came from further review and testing: a 500 is no longer taken as a refusal (the scenario "a server error after accepting" holds it to that), wait's maxPolls now counts failed reads too (a docker test makes it keep a budget of one), and a status answer naming another mission counts as a failed read, never as this mission's state.

The finding, on the first adapter's nominal run (pattern fan_out, severity low, remedy batch): This run made 6 successful GET /robots/* calls to one per-item route (the trace holds the template, not the item); a collection or batch read would cover them in one request if it returns the same items. The profile declares GET /robots as this route's batch form and grants it; the declaration is the operator's, and plimsoll has not checked that it returns the same items.

Suggested route: GET /robots, which the profile declares as the batch form of GET /robots/* and grants, so the finding came back to the caller on the run result. Measured: 5 calls beyond one, 376 bytes moved across the flagged calls; the added latency is a model (summed round trips beyond one call), not wall time lost.

The advisor is computed after the run over the broker's metadata-only trace: route templates, counts, sizes and timings, never a path, a body or a credential. It never calls a model, and it changes nothing about execution: a run with advice is byte-identical to one without. In the nominal scenario the first adapter made 26 brokered calls and the second 20; the vendor's own counts, by route, are on each run's card below.

Runs 4, 5 and 6 are the ones that matter. In run 4 the vendor accepted r2's order, started the robot, and answered with a 503 instead of the mission id. The first adapter treated the 503 as transient and sent the create again; the vendor, which queues orders for a busy robot, accepted it as a second order. The adapter's report says every mission done, and from where it stood that was true; the ledger shows two accepted orders for one command. In this simulation the second order starts where the first ended, so the robot does not move again; on a real fleet a duplicated command can be a second pick, or a second trip into space another robot was promised. In runs 5 and 6 the vendor accepted the order and then closed the connection, or answered 500; the first adapter reported the command failed, with an error the contract does not allow, while r2 was already running it. The independent trial

The exam: three fresh AIs write the adapter cold

In plain words: the first adapter on this page was written by the same AI that built the page, which is a bit like marking your own homework. So we set an exam. Three fresh agents, Claude Haiku, Claude Sonnet and Claude Opus, got the same exam paper (EXTERNAL · source repo ↗): the contract, the rules they would be judged by (six at the time; the shape and inventory rules came later and check things the contract already asked for), how the platform's client reports errors, and the vendor's API description. Open book on that, closed book on everything else. Each ran as a one-shot Claude Code session in an empty folder with every customization switched off and no tools at all, so the exam paper was the only thing in the room (well, that and the folder's name, which had "plimsoll" in it). Their transcripts were checked afterwards: no tool calls, and none of this repository's text.

Each got one practice question, the plain nominal scenario, could see how it went, and could hand in up to three times. All three aced the practice first time. Haiku handed in straight away; Sonnet and Opus each rewrote theirs anyway (after passing!) and kept the second version. The other five scenarios were the real exam, and they had not seen them. Their adapters ran here exactly as written.

    How it went. Two of the three tripped on the same question, the overloaded vendor, in the same way. They knocked on a busy door, waited about a second, and went home, leaving a polite note that said "unresolved". Honest, which counts for a lot, but the robot never got its job.       Step 5

      The boundary probe: three ways out, and a search for the key

      Run 7 is not an adapter. It is a step under the same grant that tries what hostile adapter code would try, and reports what happened. Its rules: refused by the client refused by the broker no network no credential the vendor saw nothing

      1. A catalog-only route, through the client

      refused: host api call not permitted by sandbox capability: DELETE /robots/r1

      The injected client checks the allow list before sending. That check is the guest's own code.

      2. The same route, bypassing the client

      broker answered 403 forbidden by sandbox capability allowlist

      A raw request on the broker socket, skipping the client. The broker on the host refuses it: this is the check that counts, and the trace counts it as denied.

      3. A direct request to the vendor

      failed: EPERM

      The container has no network interface but loopback. The vendor's address, which the host can reach, is unreachable from inside.

      4. The hunt for the credential. Environment entries that look like a credential: 0. The client's methods: call cancelMission createMission decommissionRobot del get getMission getRobot health listRobots patch post put updateFirmware ; none of their source mentions a bearer. The credential is minted per run on the host and attached by the broker after the route is authorized; the container never holds it. Over the 38 runs the vendor verified 37 different credentials, one per run that reached it (the probe's reached nothing): each a JWT signed for this vendor, naming the caller, living 95 s.

      Step 6

      The evidence: trust nobody on this page, check the signatures

      Two signed files sit beside this page, both signed by the attest signer's key (Ed25519, key id 23d3123cb4fbd889b5d30d049940e22f40bb021cb6a6954e1abea212da535e37, in harness.pub), a process outside the daemon:

      • bundle.jsonl, the run records. Every run answered with a record: SHA-256 digests of the request as sent and the result as returned, the provider, the tier, the environment identity and the daemon's clock. The daemon only hashes; the harness recomputed both digests before signing each.
      • qualification.jsonl, the verdicts. One statement per run, bound to that run's record by its digest: the scenario, the plan, the vendor's ledger, the credential the vendor saw, each rule's outcome and the verdict. The verifier checks each statement's adapter, plan and report against the run's signed request and output, and rebuilds the verdict from the ledger: it does not take the signer's word for the verdict, only for the ledger.
