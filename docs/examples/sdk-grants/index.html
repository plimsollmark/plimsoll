Grants for standard client libraries

The agent's code calls the OpenAI and Anthropic libraries as they ship, and never holds the key

Agent-written code reaches for the client library it knows: the OpenAI or Anthropic SDK (software development kit, the vendor's own package for calling its API). That library wants an API key, and you do not want to hand your key to an agent's code. In plimsoll, a grant (INTERNAL · glossary →), one run's permission to call listed routes of one API, can now carry what the library needs: the run's sandbox (INTERNAL · glossary →) gets a local address, the library is told to use it and is handed a dummy key, and the broker (INTERNAL · glossary →), the part of plimsolld (the plimsoll server, or daemon) outside the sandbox that makes every API call, checks each request and puts the real key on it. Below, both libraries ran unmodified that way, and the API they called wrote down everything it received.

No real model API is called on this page, and nothing is spent. The API is a stub: a small program of the example's (stub.go (EXTERNAL · source repo ↗)) listening on the host's loopback, which answers like a small part of the two APIs (a chat or messages call, the same call streamed, a file upload) and writes down every request it receives, headers and timings included. That record is what makes the key, the headers and the stream below checkable from outside the sandbox. It says nothing about how OpenAI's or Anthropic's own servers behave; the last section says what that leaves out.

Run on 2026-10-29, with openai 3.41.0 and anthropic 2.3.0 on Python 3.14.8, on one development machine. Every run's run record (INTERNAL · glossary →), plimsoll's statement of what was sent, what came back and where it ran, is signed into bundle.jsonl.

The 30-second version

1

The operator writes a grant profile (INTERNAL · glossary →), a grant stored on the server under a name: the routes it allows, the real key (named by an environment variable of the daemon's), and two new fields. sdk_env is the environment the library reads; pass_headers names the headers the broker may copy from the library's request.

2

A run that selects the profile gets plimsoll's forwarder listening on 127.0.0.1:8471 inside the sandbox, and those variables in its environment. The container still has no network: 127.0.0.1 is its own loopback, the address a machine uses to reach itself, and the forwarder hands each connection, byte for byte, to the broker's Unix socket, a local connection through a file rather than a network.

3

The broker checks the route, rebuilds the request with only the passed headers and the real key, sends it to the API, and passes the answer back: a streamed one piece by piece, as it arrives.

In the two tables: the library's key (Authorization: Bearer dummy-…) never left the broker: the API got the daemon's key in its place. The library's User-Agent gave way to the broker's own, and the x-stainless-* headers both libraries send (their telemetry: language, version, operating system, retry count) were dropped. So were the two headers the guest added on purpose: OpenAI-Organization, which would let the guest choose which organization a call is billed to, and anthropic-beta, the header that switches on a beta feature, server-side tools among them. The transport headers (Accept, Content-Type, Host and the like) are the broker's, set on every request it makes. Of the headers the library chose, only anthropic-version, which the Claude API requires and the profile lists in pass_headers, was copied through. The broker sends every key as Authorization: Bearer, which is how the Claude API documents sending an API key (authentication (EXTERNAL · official docs ↗), read 2026-10-29; x-api-key is its older header).

The stream, piece by piece

A streamed answer comes back as server-sent events (EXTERNAL · official docs ↗): one HTTP response whose body is a series of small events, written as the model produces them. The stub waited 400 ms between pieces. Had anything on the way held the answer until it ended (the broker, the forwarder or the library), every piece would have reached the library after the stub wrote the last one. Instead, each piece reached the library before the stub had written the next. The times are from one clock: the stub and the sandbox run on the same Linux kernel, and a container reads the host's wall clock.

The guest uploaded 8 MiB with client.files.create(file=("sample.bin", data, "application/octet-stream"), purpose="user_data"). A route takes a body over 1 MiB only when its profile raises the route's limit and names the type: here POST /v1/files is raised to 16 MiB and takes multipart/form-data, and the run may send 64 MiB in all.

The refusal

The guest called client.embeddings.create(model="stub-embedding", input="hello"), which is POST /v1/embeddings. The OpenAI profile allows POST /v1/chat/completions and POST /v1/files and nothing else. The library raised PermissionDeniedError, status 403, with the broker's own answer:

forbidden by sandbox capability allowlist

Three things show that the broker refused it and the API never saw it. The stub serves /v1/embeddings and would have answered 200, yet it received 0 requests there. The answer carries X-Should-Retry: false, which every answer the broker makes itself carries, and the library honors it: the attempt that raised was its first (x-stainless-retry-count: 0), so the refusal spent no further calls. And the daemon's audit line for the run counts 1 call denied by policy.

The run records, and the second seccomp profile

Each record states where its run ran: the isolation tier (INTERNAL · glossary →), how strong the wall around it was; the image, the packaged file system the sandbox started from, by its content identity; and the policy. The policy field names the seccomp (INTERNAL · glossary →) profile docker applied to the run, the kernel's list of the operations a program may ask it for, by the SHA-256 of its bytes. What this proves, and what it doesn't

Proves
  • Every run's record is signed by the harness and checks against the request and answer stored with it. (3 single runs verified, 0 sessions)
  • No request the API received carried the guest's dummy key, in a header or in a body. (0 occurrences in 5 requests)
  • Every request the API received carried the key the daemon holds for that API. (5 of 5 requests)
  • The keys the daemon holds appear nowhere in what each run was sent or answered: not in its environment, not in any process environment the guest could read, not in its output. (0 occurrences; 3 process environments read)
  • Of the guest's headers, only the one the profile passes reached the API; the broker set its own credential and transport headers. (OpenAI-Organization dropped, anthropic-beta dropped, anthropic-version passed; 0 headers leaked, altered or lost)
  • Each piece of both streamed answers reached the guest's library before the stub wrote the next one. (openai: 8 of 8 pieces before the next was written, 8 of 8 matching the stub's, first to last 2804 ms; anthropic: 12 of 12 pieces before the next was written, 13 of 13 matching the stub's, first to last 4807 ms)
  • The 8 MiB upload reached the API byte for byte, on a route raised above the 1 MiB default. (guest fa16e68dc6e4ff55, stub fa16e68dc6e4ff55)
  • The call to a route the profile does not allow was refused by the broker, marked not to retry, made once, and never reached the API. (status 403, X-Should-Retry "false", retry count "0", 0 requests at the route, 1 denied on the audit line)
  • The two runs whose grant sets sdk_env ran under the derived variant, the control run under the default, each named by digest in its record. (openai variant, anthropic variant, plain default)
  • Under the variant an IPv4 TCP socket opens and a UDP or IPv6 socket does not, and an outside address is unreachable; under the default no IPv4 socket opens. (openai IPv4 TCP allowed, UDP errno 1, IPv6 errno 1, outside address errno 101; anthropic IPv4 TCP allowed, UDP errno 1, IPv6 errno 1, outside address errno 101; control IPv4 TCP errno 1, UDP errno 1, IPv6 errno 1, outside address errno 1)
  • The guest imported the pinned versions of both libraries. (openai 3.41.0 (pinned 3.41.0), anthropic 2.3.0 (pinned 2.3.0))
  • The stub received only calls on routes the profiles allow: three from the OpenAI run, two from the Anthropic run, none from the control run. (0 off the allow lists; 3, 2 and 0)
  • The daemon's audit line for each run counts the calls the stub received, and the one refusal. (openai 3 calls 1 denied; anthropic 2 and 0; plain 0)
Doesn't prove
  • How OpenAI's or Anthropic's servers answer. The stub stands in for them, shaped like the requests the two libraries send and the answers they parse; neither vendor's API was called.
  • E2B and Docker Cloud. On those providers the sandbox is a virtual machine that reaches the broker through the guard (INTERNAL · glossary →), an HTTPS address outside it, and the guard's raw route takes a standard client's request; the documentation describes the live tests (TestE2BGuardLive, TestDockerCloudGuardLive) that send one through it with Node's fetch. sdk_env itself is not built on those providers, and none of that ran for this page.
  • That a chat API's own tools are safe to grant. The documentation's warning, quoted: “The broker checks the route and never reads the body, so everything the body can ask the API to do is granted along with the route.” A guest allowed POST /v1/messages can ask the Claude API to fetch a web page, and one allowed the Responses API can name a remote MCP (INTERNAL · glossary →) server, a program serving tools to a model; turning those tools off is done on the API's side (the warning and what to do about it (EXTERNAL · official docs ↗)).
  • Sessions, snippets, or another language's library. These were three project runs of Python code. A grant with sdk_env in a session (INTERNAL · glossary →) is refused before anything runs.
  • That the stub is honest. Its log is its own statement. The harness (INTERNAL · glossary →), the program outside the daemon that signs records, signed the log's digest beside the runs' records, which shows the log was not changed afterwards, not that it is true. The guest's side (the headers the library sent, when each piece arrived) is in each run's own output, which its record covers.
  • That the hardware is honest. The isolation tier in a record is the server's configuration, the provider's evidence and its startup checks, not a hardware attestation.

Run it yourself

From a clone of the repository (EXTERNAL · source repo ↗), with docker:

make docker-images                    # plimsoll's sandbox images, plimsoll/sandbox-python among them
go run ./examples/sdk-grants          # builds the example's image and plimsolld, runs everything, rewrites this page
go run ./examples/sdk-grants -verify  # rechecks the files beside this page; starts nothing
go run ./cmd/plimsoll-attest verify -pub docs/examples/sdk-grants/harness.pub docs/examples/sdk-grants/bundle.jsonl

The example's image is plimsoll's Python image with the two libraries installed from wheels (Python's package files) pinned by version and SHA-256 (requirements.txt (EXTERNAL · source repo ↗), 17 packages): openai 3.41.0 (EXTERNAL · package index ↗, wheel 7060a74b2396…) and anthropic 2.3.0 (EXTERNAL · package index ↗, wheel aa6a3984f927…). Building it fetches those wheels; the runs have no network. Image plimsoll-wip/sdk-grants:dev, bf5af9606ed3, built on plimsoll/sandbox-python:latest, 48666c14b387. The program spends nothing: no model, no paid sandbox. Everything on this page comes from evidence.json, which -verify rebuilds from these files:
