Dependency behavior receipt, live through plimsoll

You installed a package. Here is what its code did, signed and tied to the run that installed it.

Installing a package with npm, the package manager for Node.js (a JavaScript runtime), runs the package's install script, a command its package.json names (such as postinstall) that npm runs on the machine doing the install (npm's scripts guide (EXTERNAL · official docs ↗)). Importing the package runs its code again. Nothing in the install's output says what that code did. On this page plimsoll ran three installs, each in its own fresh sandbox (INTERNAL · glossary →) under gVisor (INTERNAL · glossary →), and for each one signed a receipt: what the programs in that sandbox did, read from outside it, and which run it was.

What a receipt is, and what made it

gVisor is a kernel written as an ordinary program: the code in the pod talks to it instead of to the machine's own kernel. Every system call (INTERNAL · glossary →) the code makes, such as opening a file, starting a program or opening a connection, is answered by gVisor. Started with its --strace option, gVisor's runsc (INTERNAL · glossary →) also writes every such call to a log file on the node (gVisor's debugging guide (EXTERNAL · official docs ↗)). The node is the machine that runs the pod, and the log file is outside the pod, where the code inside cannot write. Reading package behavior from that log is also the approach of package-analysis, the Open Source Security Foundation's tool for watching what published packages do (EXTERNAL · source repo ↗).

The receipt is what examples/dependency-receipt reads from one such log: the processes and the programs started in them, every file written, and every open for writing, file change and network call, each with its outcome. It is signed as an in-toto (INTERNAL · glossary →) statement (the Statement specification (EXTERNAL · source repo ↗)) in a DSSE (INTERNAL · glossary →) envelope, the same envelope plimsoll signs its run records (INTERNAL · glossary →) in. A run record is plimsoll's statement of one run: what was sent, what came back, and which sandbox ran it. The receipt names the log by its digest (INTERNAL · glossary →) and the run record by its digest, so it is about exactly one log and one run.

These runs used plimsoll's agent-sandbox (INTERNAL · glossary →) provider: Kubernetes, a system that runs containers across machines, keeps a warm pool of ready pods (a pod is Kubernetes' unit of one or more containers run together; Kubernetes' pods page (EXTERNAL · official docs ↗)), and each run claims one, uses it once, and deletes it. The pods ran under the RuntimeClass (INTERNAL · glossary →) gvisor-receipt, whose handler runsc-receipt is gVisor with the system-call log turned on; plimsolld, the plimsoll server, was told that handler is gVisor and held every pod to gVisor's boot line before sending it any code. All of it ran on a local kind (EXTERNAL · official docs ↗) cluster on 2026-10-29; nothing was paid for.

The three installs

Each run sent one package's files as a project and ran two steps in its pod: an offline npm install of the package from its directory (--install-links copies it into node_modules as an install from a tarball would, and runs its install script), then a node command that imports it. The packages are the fixtures beside the receipt code; none comes from the public registry, and plimsoll sends no run to a pod unless a network policy denies the pod's traffic out.

Who did what in each pod

A receipt covers the pod's whole life, not only the package: sandboxd (agent-sandbox's daemon in the pod, which starts each command plimsoll sends), plimsoll's own check of the pod, plimsoll's runner, npm, and the package. The receipt lists every process by its PID (process ID), the programs started in it, and which process made each call. This page groups the processes by the command that started them: a step's shell is matched to the step's exact text in the signed request, and an install script's shell to the script's exact text in the package.json the run sent. The grouping is the page's reading; the receipt itself lists every process and call ungrouped.

effected the call returned success, attempted it returned an error, undetermined the log does not show its outcome (the next section says more), written files written. For the package's own groups (amber) every call is listed; for the others, every call that did not succeed and every network call other than opening a new socket.

A package's own groups are short by comparison: that is what grouping by process is for.

The receipt's three sides, in plain words

Every open for writing, file change and network call in a receipt sits on exactly one of three sides, decided by what the call returned in the log.

Effected

The call returned success: it did what it asked. The network package's script sent 4 datagrams to port 53 of 127.0.0.1, the address the pod's name resolver is set to. Its source looks up canary.example, and a lookup shows in the log as a datagram to port 53, never as the name.

Attempted

The call returned an error. The canary script's open of /root/.canary answered errno=13 (permission denied), the error number and name the call returned: the code runs as user 61000 on a read-only root. Of the 77 attempted calls in the three receipts, 50 are a mkdir answering that the directory was already there (file exists) or that its parent was not there yet, and 18 are a connect to /var/run/nscd/socket, a name-service socket that does not exist in the pod. Attempted means the call failed, not that a policy stopped it, and never that the package did not try.

Undetermined

The log does not show the outcome. The network script's connect to 203.0.113.7 port 443 answered errno=115 (operation now in progress): node connects without waiting, and whether the connection ever completed is decided by calls the log does not follow. plimsoll refuses a pod unless a network policy denies its traffic out and this daemon's startup check saw all 7 outbound connections it tried from the pool's pods time out or find no route. The receipt does not lean on any of that: it says only that the connection was started.

Which run it was

plimsoll reads each claimed pod back from Kubernetes before it sends any code, and the run record names the pod by its UID, the unique ID the API server gave it when it was made. Kubernetes never gives that UID to another object in the cluster's history. runsc logs each container's spec when the pod starts, before any program in it runs, and the spec names the same UID. What the log cannot show

A receipt is exactly as good as the log under it. These are its limits, stated in the receipt code's README; nothing on this page gets around them.

  • The log is the signer's word. Whoever runs the node holds the log. The check proves the receipt says exactly what this log shows and names this run; it cannot prove runsc wrote this log for that pod.
  • Behavior the package keeps for later. One install and one import is one observation. Code that waits, or checks whether it is watched, shows nothing.
  • Names looked up in DNS show as datagrams to port 53, not the names.
  • The destination of a datagram sent with sendmsg, which node's UDP sockets use: the network script's datagram to 198.51.100.9 is in its receipt as one send with no destination.
  • Writes through shared memory mappings, sendfile, splice, copy_file_range and fallocate are outside the calls the log keeps, so an open for writing can appear with no write after it.
  • Paths of calls that take no descriptor (mkdir, rename, unlink, open) are read from the program's memory before the call reads them, so a second thread can change them in between, and a symlink in a folder of the path can make the call land elsewhere. Files written are named from descriptors and are not affected.
  • Starting a new program can close descriptors silently, so after one the reader leaves a descriptor's name unresolved rather than give it a new file's name.
  • io_uring, Linux's interface for queued file and network work, which runsc leaves off unless started with --iouring; the receipt is refused for a log made with it on.
  • Anything outside gVisor. plimsoll's providers that run each sandbox in a small virtual machine of its own (Kata Containers, E2B, Docker Cloud) have no such log, so no receipt.
  • The whole pod is one observation. sandboxd, plimsoll's check, the runner and npm are in every receipt with the package; this page's grouping is a reading of the process tree, not part of the signed claim.
  • This cluster is a local test setup. The pod network between plimsolld and sandboxd is kind's default, which is not encrypted, so these runs show the receipt, not a protected channel (plimsoll's agent-sandbox guide (EXTERNAL · source repo ↗)). The daemon was not in hardened mode (INTERNAL · glossary →), and the image is named by tag; each run's record states the image's digest as the node reported it.

Every receipt also signs this list of what it cannot see, so its limits travel with it:

  • behavior the package keeps for later: one install and one import is one observation, and code that waits, or checks whether it is watched, shows nothing
  • names looked up in DNS: a lookup shows as a datagram to port 53, not the name
  • the destination of a datagram sent with sendmsg
  • writes through shared memory mappings, sendfile, splice, copy_file_range and fallocate
  • paths of calls that take no descriptor are copied from the program's memory before the call reads them, so a second thread can change them in between; files written are named from descriptors and are not affected
  • the pod's whole life is one observation: a pod that served several calls shows all of them
  • anything outside gVisor

-verify checks the bundle's signatures and chain, checks every receipt against its log and record, requires both changed inputs and the wrong record to be refused, and requires this page to be exactly what evidence.json renders. Running everything again needs a kind cluster with agent-sandbox and the gvisor-receipt runtime class: go run ./examples/dependency-receipt/live makes a Kubernetes namespace (a named group of the cluster's objects) of its own and deletes it after.
