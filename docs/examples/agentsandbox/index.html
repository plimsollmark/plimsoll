plimsoll on Kubernetes agent-sandbox: signed runs, their bills of materials, and five refusals

plimsoll is a service that runs code an AI agent wrote and says, on every run, behind which boundary it ran. Kubernetes agent-sandbox is a Kubernetes project that keeps sandboxes as pods (Kubernetes' unit of one or more containers) in a warm pool, started ahead of time so a run does not wait for one. This page is two real runs through plimsoll on agent-sandbox, recorded on 2026-10-18 04:23:27 UTC, each signed and converted into a bill of materials, and five things plimsoll refused to do on the same cluster. Every claim below is either signed, and checkable with the commands at the end, or marked as a transcript.

Words this page uses

  • Tier: how strong the wall between the code and the machine is. container is an ordinary container (runc): the code talks to the machine's own kernel through a filter. kernel is gVisor: a stand-in kernel that runs as an ordinary program, so the code never talks to the machine's kernel directly. vm is a separate virtual machine.
  • Runtime class: the Kubernetes object a pod names to pick how its containers start. Its handler is a name, runsc for gVisor or runc, which each node maps to a program in its own configuration. The Kubernetes API shows the name, never the mapping.
  • Floor: the weakest tier a request accepts. A provider that cannot meet it refuses before anything runs.
  • Run record: what the daemon states about one run: SHA-256 digests (fingerprints that change if one byte changes) of the request and the result, the provider, the tier, the image, the times. A harness outside the daemon checks each record against the request and result it saw and signs it with its own key, into a bundle file.
  • Bill of materials (BOM): a parts list. CycloneDX is a standard format for it that supply-chain tools read; here each run's BOM lists the program's files, the image, the steps, and the record's claims, with the signed evidence attached.
  • Hardened mode: plimsoll's strict start. It refuses to serve unless every production rule holds: a VM or verified gVisor, a pinned image, per-caller authentication and limits, a stated memory, CPU and disk budget.

What happens on each run

Step 4 is new. A handler's name is configuration on each node, which the Kubernetes API does not show, so before any of the run's code plimsoll runs one command of its own in the claimed pod, as the guest: the first line of the kernel log, which under gVisor is gVisor's own boot line, and the seccomp mode, which under runc must show a filter. The pod is fresh, so nothing of a guest's has run in it yet. On this cluster the check cost nothing measurable: the median snippet took 75 ms from claim to result with it and without it, over ten runs each. Refusal 4 below is why it exists.

Five refusals

Each of these is a transcript, unsigned: a refusal made before any code ran leaves no run record, since there is no result to state. The caller's lines are what plimsoll-attest run printed; the daemon's line is from its log, where an environment refusal's detail is kept, since it can carry the cluster's own error text.

1. The template edited under a running daemon

What was done

With the hardened daemon serving, one environment variable was added to the template's container, a field the per-run read-back does not decode, and the reconcile request was sent again.

What the caller got
plimsoll-attest: refused before dispatch (reason environment), so nothing ran; the bundle is unchanged: internal: internal error eb60cffd4ea34aee; the daemon's log holds its detail
What the daemon logged
agentsandbox: template evidence-gvisor changed after the startup smoke test proved it; plimsoll runs only on the template it proved, so restart plimsolld to prove this one
Then

With the edit removed, the next request was refused too, reason isolation, because the failed check had set the daemon's tier to unknown (“failed_precondition: sandbox isolation requirement not met: provider isolation unknown is below requested minimum kernel”). Readiness proved the template again 7 seconds after the edit was removed, and the same request then ran (“ran on agentsandbox (kernel): PROJECT_OUTCOME_COMPLETED, 2 steps”).

What it shows

Once the startup smoke test passes, only the template it proved runs, as a docker image tag re-pointed after startup is refused. A field plimsoll does not read cannot change under a running daemon.

2. Hardened mode on the runc pool

What was done

The same hardened settings, pointed at the pool whose runtime class names runc.

What the daemon logged
provider "agentsandbox" reports isolation "container"; hardened mode requires vm (e2b, dockercloud) or verified kernel (docker with SANDBOX_DOCKER_RUNTIME=runsc, agentsandbox on a runsc runtime class)
Then

The daemon did not start.

What it shows

runc is an ordinary container, the container tier, and hardened mode serves only a VM or a verified user-space kernel.

3. A kernel floor on the runc pool

What was done

The same settings without hardened mode: the daemon started at the container tier (its smoke test found a seccomp filter in force, mode 2), and the reconcile request, whose floor is kernel, was sent to it.

What the caller got
plimsoll-attest: refused before dispatch (reason isolation), so nothing ran; the bundle is unchanged: sandbox isolation requirement not met
failed_precondition: sandbox isolation requirement not met: provider isolation container is below requested minimum kernel
Then

No pod was claimed.

What it shows

The floor is the caller's: a request states the weakest tier it accepts, and a provider that cannot meet it refuses before anything runs.

4. A runsc handler that is not gVisor, under a running daemon

What was done

With the hardened daemon serving after a passing smoke test under gVisor, the node's containerd configuration was edited so that its runsc handler starts ordinary runc containers, and the pool's pods were recreated. The runtime class still names runsc, so the Kubernetes API shows nothing different. A snippet that prints the kernel version was then sent.

What the caller got
plimsoll-attest: refused before dispatch (reason environment), so nothing ran; the bundle is unchanged: internal: internal error 63a568140598488b; the daemon's log holds its detail
What the daemon logged
agentsandbox: claim plimsoll-757ad683977cf1c7: the runtime class's handler is runsc but the guest's kernel log begins "[178435.536685]  dump_header+0x51/0x260", not gVisor's
Then

Before the fix this recording led to, the same setup let a daemon run this snippet and sign it at the kernel tier.

That run's record is published, signed by the same harness key: INTERNAL · before-the-fix.jsonl →, record 106b10d3df55…, provider agentsandbox, tier kernel, exit 0. What the snippet printed:

Linux version 6.6.87.2-microsoft-standard-WSL2 (root@439a258ad544) (gcc (GCC) 11.2.0, GNU ld (GNU Binutils) 2.37) #1 SMP PREEMPT_DYNAMIC Thu Jun  5 18:30:46 UTC 2025
Seccomp:	0

The signature is genuine and the claim was wrong: a signature proves who stated a record and that it was not changed, not that the statement was true. That is why the tier has to be checked where the code runs.

What it shows

A handler's name is configuration on each node, which the Kubernetes API does not show. So plimsoll's first command in every claimed pod, before any of the run's code, reads the kernel log and the seccomp mode as the guest, and a pod that does not match its tier is refused.

5. The same node, a fresh daemon

What was done

A new hardened daemon started against the remapped node.

What the daemon logged
sandbox smoke test: agentsandbox smoke: boundary test: agentsandbox: claim plimsoll-ded06d7ff709ec7b: the runtime class's handler is runsc but the guest's kernel log begins "[178435.536685]  dump_header+0x51/0x260", not gVisor's
Then

The daemon did not start. The node was then restored and the pool's pods recreated under gVisor.

What it shows

The startup smoke test claims pods as runs do, so it meets the same check.

What the startup smoke test proved

Before serving, the daemon claimed two pods as runs do and checked from inside what reading the configuration cannot show. Under gVisor: the kernel log begins [ 0.000000] Starting gVisor...; of 4902 paths the guest could reach, writes succeeded only in /dev/shm, /tmp, /work; each volume refused writes once full (/tmp 32 MiB then ENOSPC; /work 128 MiB then ENOSPC); and every connection out failed:

Check it yourself

From a checkout of the repository. The first command checks every signature, digest and link in the bundle; the second rebuilds a bill of materials from the signed line it attaches and compares it, pinning the harness key you trust.

go run ./cmd/plimsoll-attest verify -pub docs/examples/agentsandbox/harness.pub docs/examples/agentsandbox/bundle.jsonl
cd examples/sbom
go run . -check ../../docs/examples/agentsandbox/run-e25b11e37738.cdx.json \
  -trusted-pub ../../docs/examples/agentsandbox/harness.pub \
  -check-bundle ../../docs/examples/agentsandbox/bundle.jsonl
cd ../..
go run ./examples/agentsandbox   # writes this page again from the files beside it

The harness key is the CycloneDX example's (key ID 88d311fb942e0fd87cdb1214b385db5fc354c166e84763f6d37885dbc96df379): one operator's harness signed both pages' runs.

How this was recorded

  • A kind cluster (Kubernetes in docker, one node) on one developer machine: Kubernetes 1.37.0, containerd 2.3.4, agent-sandbox v1.0.7, gVisor release-20260907.0.
  • The pool's template is the one in EXTERNAL · source repo ↗, with the image pinned by the digest above and plimsolld's network as the only source allowed in.
  • plimsolld ran in a container on the cluster's network, since it reaches each pod's sandboxd at the pod's address, in hardened mode: a callers file, the pinned image required, 256 MiB, 1 CPU and 160 MiB of disk per run, 60 runs a minute per caller.
  • Refusals 4 and 5 needed root on the node: its containerd configuration was edited, which no caller and no pod can do. They stand for a node that joins a pool misconfigured, not for an attack.
  • The operator guide is EXTERNAL · source repo ↗.

What this does not show

  • A tier is configuration and provider evidence plus these checks, never attestation. gVisor's boot line is text a node's root could forge; the check catches a misconfigured node, not a hostile one.
  • One node on one machine. On a cluster of many nodes, each run's own check covers the node it lands on, and the startup smoke test covers only the nodes its two pods landed on.
  • Memory: on a node with swap, a gVisor pod can hold more than its limit (measured on this cluster: a 128 MiB pod held 1024 MiB, 932 of it in swap, where runc killed the same pod at 112 MiB). That is gVisor's open issue 15756, not something plimsoll can see from the API; the operator guide gives the node setting that stops it.
  • The refusals are transcripts. Only the two runs are signed.
