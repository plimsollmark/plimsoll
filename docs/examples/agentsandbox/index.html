plimsoll on Kubernetes agent-sandbox: signed runs, their bills of materials, and five refusals

plimsoll is a service that runs code an AI agent wrote and says, on every run, behind which boundary it ran. Kubernetes agent-sandbox is a Kubernetes project that keeps sandboxes as pods (Kubernetes' unit of one or more containers) in a warm pool, started ahead of time so a run does not wait for one. This page is the same two real requests run through plimsoll as agent-sandbox under gVisor (recorded 2026-10-23 20:09 UTC) and agent-sandbox under Kata Containers (recorded 2026-10-23 20:10 UTC), each run signed and converted into a bill of materials, what a pod's kernel said in the vm room, and five things plimsoll refused to do on the same cluster. Every claim below is either signed, and checkable with the commands at the end, or marked as a transcript.

Words this page uses

  • Tier: how strong the wall between the code and the machine is. container is an ordinary container (runc): the code talks to the machine's own kernel through a filter. kernel is gVisor: a stand-in kernel that runs as an ordinary program, so the code never talks to the machine's kernel directly. vm is a separate virtual machine with a kernel of its own: here Kata Containers, which starts each pod inside a small virtual machine, and a Docker Cloud microVM.
  • Runtime class: the Kubernetes object a pod names to pick how its containers start. Its handler is a name, runsc for gVisor, kata-clh-runtime-rs for Kata on the Cloud Hypervisor, or runc, which each node maps to a program in its own configuration. The Kubernetes API shows the name, never the mapping.
  • Boot ID: a random identifier a Linux kernel picks each time it starts, which any process can read. Two processes that read the same boot ID run on the same kernel.
  • Room: one place the same request ran, named by its provider, the tier the provider stated and, on agent-sandbox, the runtime class.
  • Floor: the weakest tier a request accepts. A provider that cannot meet it refuses before anything runs.
  • Run record: what the daemon states about one run: SHA-256 digests (fingerprints that change if one byte changes) of the request and the result, the provider, the tier, the image, the times. A harness outside the daemon checks each record against the request and result it saw and signs it with its own key, into a bundle file.
  • Bill of materials (BOM): a parts list. CycloneDX is a standard format for it that supply-chain tools read; here each run's BOM lists the program's files, the image, the steps, and the record's claims, with the signed evidence attached.
  • Hardened mode: plimsoll's strict start. It refuses to serve unless every production rule holds: a VM or verified gVisor, a pinned image, per-caller authentication and limits, a stated memory and CPU budget, and below the vm tier a disk budget.

What happens on each run

Step 4 is new. A handler's name is configuration on each node, which the Kubernetes API does not show, so before any of the run's code plimsoll runs one command of its own in the claimed pod, as the guest. Under gVisor the first line of the kernel log must be gVisor's own boot line. Under Kata it must be a Linux kernel's boot line, and the kernel's boot ID must differ from the one the pod's node reports through the API, since a pod started on the node's own kernel shares the node's boot ID. Under runc the seccomp mode must show a filter. The pod is fresh, so nothing of a guest's has run in it yet. On this cluster the check cost nothing measurable under gVisor: the median snippet took 75 ms from claim to result with it and without it, over ten runs each. Refusal 4 below is why it exists, and the vm room's section shows what it reads in a pod of that room.

What this room shows

  • The same two requests, byte for byte, sent to a hardened plimsolld whose runtime class names a Kata handler, ran to completion at the vm tier, and their results are byte for byte the gVisor room's.
  • Each pod ran a Linux kernel of its own: the kernel log begins with Linux 6.18.35's boot line, the kernel Kata boots, where the node runs 6.6.87, and the guest's boot ID is not the one the node reports. Those are the two things plimsoll's per-pod check reads, and each run above passed that check, or it would have been refused before any of its code ran.
  • The startup smoke test held the pool to the vm tier's rules before the daemon served: the guest could write only to tmpfs mounts of its own kernel, so into the VM's memory, and every connection out timed out.

What it does not show

  • A tier is configuration and provider evidence plus the startup smoke test and the per-pod check, never runtime attestation. The boot line and the boot ID are what the guest reads, and a node's root could forge both: the check catches a node whose Kata handler starts something other than a VM, not a hostile node.
  • Kata on kind is nested virtualization on a laptop: the kind node is a container on the laptop's Linux virtual machine, and each Kata VM runs under KVM inside that one. It is not a cloud deployment, and it says nothing about the speed or memory a cloud node would give.
  • The values in the table come from a third pod of the same pool, read by a signed snippet after plimsoll's own check had passed in that pod. The two project runs' pods passed the same check (a pod that fails it is refused before any code is sent), but plimsoll keeps none of the values the check read.
  • No volume kept its size limit: Kata mounts each memory-backed volume as a tmpfs of the VM's kernel with no size of its own, so the daemon ran with no disk budget, and a run's writes are bounded by the VM's memory, not by the template's limits.
  • No seccomp filter inside the guest (Seccomp 0 in the snippet's output): Kata applies none unless its configuration asks for one, and plimsoll requires none at this tier, where the boundary is the VM.
  • This room has no refusal of its own on this page. With the node's Kata handler pointed at runc, every run and the startup smoke test were refused on both counts when that was measured on 2026-10-18; the operator guide records it, and it was not recorded here.

Five refusals

Each of these is a transcript, unsigned, recorded on this cluster on 2026-10-18 04:23:27 UTC, with the first room's earlier runs; the rooms' signed runs above were made again on the dates they state, for record version 4: a refusal made before any code ran leaves no run record, since there is no result to state. The caller's lines are what plimsoll-attest run printed; the daemon's line is from its log, where an environment refusal's detail is kept, since it can carry the cluster's own error text.

1. The template edited under a running daemon

What was done

With the hardened daemon serving, one environment variable was added to the template's container, a field the per-run read-back does not decode, and the reconcile request was sent again.

What the caller got
plimsoll-attest: refused before dispatch (reason environment), so nothing ran; the bundle is unchanged: internal: internal error eb60cffd4ea34aee; the daemon's log holds its detail
What the daemon logged
agentsandbox: template evidence-gvisor changed after the startup smoke test proved it; plimsoll runs only on the template it proved, so restart plimsolld to prove this one
Then

With the edit removed, the next request was refused too, reason isolation, because the failed check had set the daemon's tier to unknown (“failed_precondition: sandbox isolation requirement not met: provider isolation unknown is below requested minimum kernel”). Readiness proved the template again 7 seconds after the edit was removed, and the same request then ran (“ran on agentsandbox (kernel): PROJECT_OUTCOME_COMPLETED, 2 steps”).

What it shows

Once the startup smoke test passes, only the template it proved runs, as a docker image tag re-pointed after startup is refused. A field plimsoll does not read cannot change under a running daemon.

3. A kernel floor on the runc pool

What was done

The same settings without hardened mode: the daemon started at the container tier (its smoke test found a seccomp filter in force, mode 2), and the reconcile request, whose floor is kernel, was sent to it.

No pod was claimed.

What it shows

The floor is the caller's: a request states the weakest tier it accepts, and a provider that cannot meet it refuses before anything runs.

How this was recorded

  • A kind cluster (Kubernetes in docker, one node) on one developer machine, a laptop: Kubernetes 1.37.0, containerd 2.3.4, agent-sandbox v1.0.7. The example template the pools start from is in EXTERNAL · source repo ↗.
  • agent-sandbox under gVisor, recorded 2026-10-23 20:09 UTC: runtime class gvisor, handler runsc, gVisor release-20260907.0. The pool's template is the operator guide's example template, with the image pinned by its digest and plimsolld's network as the only source allowed in. plimsolld ran in hardened mode: a callers file, the pinned image required, 256 MiB, 1 CPU and 160 MiB of disk per run, 60 runs a minute per caller.
  • agent-sandbox under Kata Containers, recorded 2026-10-23 20:10 UTC: runtime class kata-clh-runtime-rs, handler kata-clh-runtime-rs, Kata Containers 4.2.0 (installed by its kata-deploy chart), Cloud Hypervisor on runtime-rs, Kata's Rust runtime; each pod is a virtual machine sized to the pod's 256 MiB, plus a fixed 130 MiB and 250 millicores the runtime class adds for the VM. The pool's template is the gVisor room's, with one line changed: the runtime class. plimsolld ran in hardened mode with the same settings except the disk budget, which the vm tier refuses because no volume keeps its size limit under Kata.
  • Each daemon ran in a container on the cluster's network, since it reaches each pod's sandboxd at the pod's address.
  • Refusals 4 and 5 needed root on the node: its containerd configuration was edited, which no caller and no pod can do. They stand for a node that joins a pool misconfigured, not for an attack.
  • The operator guide is EXTERNAL · source repo ↗.

What this does not show

  • A tier is configuration and provider evidence plus these checks, never attestation. gVisor's boot line is text a node's root could forge; the check catches a misconfigured node, not a hostile one.
  • One node on one machine. On a cluster of many nodes, each run's own check covers the node it lands on, and the startup smoke test covers only the nodes its two pods landed on.
  • Memory: on a node with swap, a gVisor pod can hold more than its limit (measured on this cluster: a 128 MiB pod held 1024 MiB, 932 of it in swap, where runc killed the same pod at 112 MiB). That is gVisor's open issue 15756, not something plimsoll can see from the API; the operator guide gives the node setting that stops it.
  • What agent-sandbox under Kata Containers does not show is listed in its own section.
  • The refusals, the smoke tests and the node's side of the pod check are transcripts. Only the runs are signed.
