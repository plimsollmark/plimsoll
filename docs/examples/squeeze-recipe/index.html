A plimsoll example · the squeeze test, with a scrambled recipe

Does a fresh AI agent follow the plan it is handed?

I gave 40 fresh AI agents (an AI left alone with a job and a terminal: it writes code, runs it, reads what happened and tries again, like a new hire on their first day) the same small job: write the program that flies a simulated drone through three gates and lands it on a pad. Of those, 16 also got a plan: a short recipe of 32 tokens (the pieces a language model reads text in; a short word is usually one token, so this is about 23 words) left behind by an earlier AI that had learned to fly this course well. Think of it as the sticky note the last person on the job left for you. Another 16 got the same sticky note with its words cut apart and glued back in a random order. And 8 got no note at all. Then plimsoll, a sandbox that runs untrusted code and signs a record of every run, graded each agent's program on 64 flights no agent had seen, like a final exam kept in a sealed envelope.

The short answer, in three parts. First, the order of the words mattered: agents with the honest recipe landed more flights than agents with the same words shuffled, by a margin bigger than luck alone would give, under a rule for reading the result that was written down before the run. Second, the honest recipe did not clearly beat having no recipe at all; its lead there is small enough to be luck. So the shuffled words look more like they hurt than the honest recipe looks like it helped (my reading, not the registered measure). Third, when the code was searched for the recipe's own words, none of the recipe or shuffled-recipe agents had used any of the recipe's 7 named parts, and every one of the 16 honest-recipe agents, asked afterward, said it had followed the recipe "only partly" or "only in part". Every number is below, marked good, bad or inconclusive, with the agents' own words.

Whose experiment this is

This experiment was built from three suggestions by Ayan Shaikh, who builds AI red-team agents (programs that attack a computer network to test its defenses), and whose two papers it draws on: "No One Architecture Fits All: A Cross-Environment Evaluation of Hierarchical Red Team Agents" (EXTERNAL · article ↗) and "A Red Teaming Framework for Evaluating Robustness of AI-enabled Security Orchestration, Automation, and Response Systems" (EXTERNAL · article ↗). Each suggestion shaped it:

  • Score by what changed, never by what the agent says it did. The landings come from signed grading runs; the agents' own accounts are kept apart and enter no score.
  • Shuffle the plan and see whether the agent's actions change. That is the shuffled-recipe group, this experiment's main comparison, and it found that the order of the words mattered. The chart below shows what is compared and how to read it.
  • Ask whether hiding the simulator would send agents hunting for another shortcut. The simulator never entered an agent's sandbox, and no controller carried a random number generator (0 of 16 honest-recipe, 0 of 16 shuffled-recipe and 0 of 8 no-recipe controllers did).

How to read it.

  • What is compared: the average share of the 64 sealed flights landed by the 16 honest-recipe agents (88.0%) and by the 16 scrambled-recipe agents (80.3%), whose recipe had the same words shuffled. Higher is better: more of the flights ended on the pad.
  • The gap: 88.0% minus 80.3% is 7.7 percentage points (the plain difference between two percentages), about 5 more landings for every 64 flights.
  • The 95% interval: 16 agents is a small class, so a rerun with new agents would give a somewhat different gap. The interval, +2.8 to +12.6 points, is the range the real gap plausibly sits in. Even its low end is above zero, so luck alone would rarely make the honest recipe win by this much. With groups this small, read the range as a bit optimistic (the 95% entry below says why).
  • No recipe: 85.5%, only 2.4 points behind the honest recipe, and that gap's interval (-1.5 to +6.4) holds zero, so it could be luck.

Why only partly? The likely reason, in the agents' own words

This is a reading of what the agents wrote, not a measured result. Every agent started from the same working baseline controller, a plain program that already flies the course roughly. Most of the honest-recipe agents bolted a few of the recipe's cheapest ideas onto that baseline, flew their four smoke flights, saw them pass, and stopped. Many said they stopped once those flights passed, and some said they left parts out because they could not see inside the simulator to tune them. Two of them, in their own words:

the baseline plus these small changes passed all four smoke flights and all eight random flights on the first try. With no failures to diagnose, I stopped there instead of adding complexity I couldn't show was needed.easy.recipe.0, honest recipe, 57 of 64 fresh flights

I took the quickest route, which was to patch the baseline and fly it.easy.recipe.3, honest recipe, 58 of 64 fresh flights

So the most probable reason is that the course was easy enough, and the starting point good enough, that a full plan was never needed to pass the tests the agents could see. A plan gets followed when following it is the shortest road to a passing grade.

A proposal for a next run (not done here): start every agent from a baseline that cannot fly the course on its own, so that the recipe is worth more than a quick patch, and grade the practice flights on a harder course, where a patched baseline does not already land most flights. Then the recipe's costly parts, the ones every agent here skipped, would have to earn their place, and the code measure would have something to find. And give the control group a note that reads well but is wrong for the course (the harder course's recipe, say) instead of shuffled words, so that a win for the honest recipe means its content was used and not only that garbled text got in the way (section 5 says why that matters).

How to read these numbers
  • 85.5% with no recipe is the yardstick. It is what a fresh agent does on this course with the baseline and nothing else. A recipe helps only if it beats that; the gap between the groups is the story, not the size of any one number.

1The question

A plan only helps if it is followed. The squeeze test (INTERNAL · example →) asks fresh agents to rebuild a working controller (INTERNAL · glossary →), the program that flies the drone, from a 32-token recipe. This experiment asks whether the recipe did anything. The control is the recipe's own words in a shuffled order: the same ingredients, no method. If the agents ignore the recipe, the shuffled one should do just as well, and their code should look the same. If they follow it, the honest order should win.

Two measures, both read by code and never from an agent's own account of itself:

  • Fresh flights landed, of 64: each agent's final controller graded in sandboxes of its own on the sealed flights. What happened in the simulator is the score.
  • Recipe words named in code, of 7: the recipe lists 7 items, each a flying technique with a name (a filter that smooths the speed reading, a part that estimates the wind, and so on). An item counts when a name in the agent's final code matches one of that item's word patterns, with comments removed and the names the shared starting controller already had left out. It measures whether the recipe's words were taken up, not whether the code does what they say (section 6 has the patterns).

And one thing gathered by asking. Once each session was over, the agent was asked, with no tool left to run:

Your session is over. Nothing you do now changes your controller or its score, and no tool will run. In a few sentences: did you follow the recipe you were given? Which parts did you use, which did you change or leave out, and why?

(The no-recipe agents were asked what approach their controller took, and why.) The answer changes nothing about the score. It is on the page because what an agent says it did and what its code does are different things, and the experiment can show both.

2The setup

  • The model. Claude Sonnet 5.5, model id claude-sonnet-5-5 (the exact version name a program asks for), through the Messages API, the way a program sends the model a request over the internet and gets its answer back; each agent a fresh session with no memory of the others. The model ran on its maker's servers, outside plimsoll. The calls to it went through a small relay program on the experimenter's own machine that enforced the spending cap, which is why each stage's run.json names a local address as model_base (http://127.0.0.1:37749, then http://127.0.0.1:42949). plimsoll ran and signed the code the agents wrote, not their thinking.
  • The job. The squeeze example's easy drone course: fly through three gates in order, then land on a pad, within 25 seconds, in a simulated room with hidden wind and gusts, a hidden payload of up to 0.25 kg and one motor up to 25 percent weaker than the others. Every agent started from the same baseline controller, a plain program that steers toward one waypoint after another, and the same course description.
  • The tools. write_file writes a file, run_code runs JavaScript or Python in the agent's own sandbox (INTERNAL · glossary →), and fly flies its controller.js in a separate sandbox that holds the simulator and answers with each flight's result. The agent's own sandbox never held the simulator, so it could practice but not peek.
  • The budget, the same for every group. 30 turns (one turn is one answer from the model, with the tool calls it makes), and up to 20 fly calls of up to 8 new random flights each, plus the 4 smoke flights the course names (a quick first check, open to every agent). Practice is limited, and the reason is cost.

The honest recipe is the note an earlier AI wrote about this course, counted at 32 tokens by Gemini's tokenizer (count_tokens on gemini-4-argon), as the hackathon counted it. (That AI learned the course over many rounds of trying and fixing in the did-it-learn hackathon entry the course comes from; "honest" means it flew the course for real rather than memorizing the test flights.) The scrambled note is its words shuffled by a fixed seed. Below, the honest note is cut at its semicolons into its 7 items, and each word of the scrambled note carries the number of the item it came from, so you can see the shuffle.

Each group's brief ends differently; after the course description, a recipe agent read:

A builder before you worked on exactly this task for a long time. Everything it learned was compressed into this recipe, which is all you get from it:

    Filter velocity; fast/slow accel disturbance observer; yaw + local pos integrals; smooth ref filter; gate exit lock; predictive cross abort; ramp pad descent.

Build controller.js following the recipe. You may fly the smoke flights and any new flights you choose; you will not see the flights you are graded on. Leave your best version in controller.js, and end your reply with one line: SMOKE=<passed>/4.

and a no-recipe agent:

Build the best one you can in controller.js. You may fly the smoke flights and any new flights you choose; you will not see the flights you are graded on. Leave your best version in controller.js, and end your reply with one line: SMOKE=<passed>/4.
  • Two stages. The 8 no-recipe agents ran first, from 12:31 to 12:42 UTC on 2026-11-07, to measure how hard the course is before anything else was spent. Had they landed 90% or more of the fresh flights, the rule would not read landings at all, since a course that easy leaves no room for a plan to help. They landed 85.5%, so the second stage ran: 16 recipe and 16 scrambled agents, started in turn, from 12:46 to 13:22 UTC, 4 minutes after the first stage ended. Same model id, same sealed flights.
  • The grading. Every final controller was graded in sandboxes of its own, 10 grading runs a controller of at most eight flights each: the 16 practice flights (the flights the earlier AI had tuned itself on) and the 64 fresh ones. Each flight had a 5-second budget of the controller's own computing time. The fresh flights were sealed by the SHA-256 d81c7b18c6cf2ade… before the first agent ran, and both stages flew exactly that set.
  • The sandboxes. plimsoll's docker provider under gVisor (INTERNAL · glossary →), isolation tier (INTERNAL · glossary →) kernel. Every call into a sandbox was signed into a bundle (one file holding every run's signed record) by a signing key (INTERNAL · glossary →) made for its stage; the private half was never written.

4The registered rule, and what it says

The rule was written down before the first agent ran. Its words are in experiment.json beside this page, and this page's program applies them by code; the record of when they were written is not public, so you can read the rule here but not check its date from this page alone. It resamples agents within each group 10,000 times (seed 20261106) and tries its four outcomes in this order, stopping at the first that fits:

  • ORDER SHOWEDthis run
    recipe minus scrambled has its 95% interval above zero on recipe words named in code, or on landings when they are read: the recipe in its order moved the words the code names, or the landings, beyond the same words shuffled. It does not show the code does what the recipe says.
  • WORDS ONLY
    not that, but recipe minus none and scrambled minus none both have their 95% intervals above zero on recipe words named in code: the agents took up the words, and the order they came in did not show.
  • NO RECIPE EFFECT SEEN
    recipe minus scrambled has its 90% interval inside the margin (1 item of words; 10 points of landings, when read), and so does recipe minus none on words: the recipe moved nothing these two measures can see.
  • INCONCLUSIVE
    anything else.

What decided it. Recipe minus scrambled, on landings: +7.7 points (about 5 flights of 64), 95% interval +2.8 to +12.6, wholly above zero. Landings were read, because the no-recipe group landed 85.5%, under the 90% line. On recipe words named in code, recipe minus scrambled was 0 with a 95% interval of 0 to 0, so words did not decide it: the landings did.

So, in the rule's words: ORDER SHOWED. The recipe in its order moved the landings beyond the same words shuffled. It does not show the code does what the recipe says.

5Good, bad or inconclusive

The scale: GOOD means this run gives evidence that the agents used what they were handed; BAD means evidence that they did not, or a weakness of this run that limits what it can say; INCONCLUSIVE means this run cannot tell either way. These marks are my rating of each finding, not the registered rule's outcome, which is in section 4.

GOOD

The recipe's order moved the landings

The honest recipe's agents landed 88.0% of the fresh flights; the scrambled recipe's, 80.3%: +7.7 points, 95% interval +2.8 to +12.6. By the registered rule, ORDER SHOWED: the same words did better in their honest order than shuffled, so the order of what an agent was handed changed how its program flew.

INCONCLUSIVE

Does the honest recipe beat no recipe? Not that this run can see

Recipe minus none: +2.4 points, 95% interval -1.5 to +6.4, which holds zero. Scrambled minus none: -5.3 points, 95% interval -11.0 to +0.6, which holds zero too, only just: its 90% interval, -10.2 to -0.4, does not.

My reading, which is not the registered measure: the order effect looks more like the shuffled words hurting than the honest recipe helping. A shuffled plan is not nothing; it is noise the agent has to read and decide about.

What the comparison cannot separate. The control was the plan's own words shuffled into nonsense. So "the honest order won" can mean two different things: that the agents took something from the plan's content, or only that a garbled note costs an agent something (time, confusion, a worse starting idea) that a clear note does not. This run cannot tell those two apart. A next run could, by giving the control group a note that reads well but is wrong for this course: the recipe written for the harder drone course, or the same 7 items kept whole and reordered, or a plausible recipe for a different task. If the honest recipe still wins against a coherent wrong plan, the content mattered; if not, it was the garbling. That is a proposal, not something done here.

BAD

No recipe item reached the code by name

Of the recipe's 7 items, the honest recipe's controllers name 0 on average and the scrambled recipe's 0: not one controller in either group adds a name that matches any item. With no recipe, one agent did, by chance: easy.none.4 named "gate exit lock".

BAD

What the agents say they used, their code does not name

Asked afterward, all 16 of the 16 honest-recipe agents said they followed the recipe only partly or only in part, and 12 of them described pieces they used "in simplified form". (12 of the 16 scrambled agents also said only partly or only in part.) The code measure finds none of the pieces named. Recipe agent 0 is one case:

Only partly. I started from the baseline follower and added a few recipe-like pieces, but I did not build the full recipe.easy.recipe.0, honest recipe, 57 of 64 fresh flights

It lists a velocity filter, local position integrals and "a crude version of the recipe's abort". In its controller the word "abort" sits only in a comment, which the measure removes, and the filter and the integrals have names that carry none of the recipe's words (section 6 shows the lines).

Neither side of this shows behavior: an account is the agent's word, and a name is only a name. Read by eye, for this one controller and not as a measure, the code does hold a filter on velocity, x and z integrals and a step back to lining up near a gate, under short names the patterns cannot match. So the name count can miss real pieces, and it cannot confirm the accounts either. Checking whether code does what a recipe says needs a test of what the code does, which this experiment did not have.

BAD

One easy course, close to its ceiling

With no recipe at all, agents already landed 85.5% of the fresh flights, near the 90% line past which the rule would not read landings. A plan has little room to help on a course this easy. One model, one recipe and one course: the result says nothing about a harder course or another model.

Every agent, and every answer

All 40, in the order they were built. Open one to read its whole answer, exactly as it came back (the model writes markdown; its bold and lists are kept, nothing else).

  • easy.none.0 · 52 of 64 fresh · 13 of 16 practice · 10 turns · 6 fly calls
    Quoted its recipe: no · recipe words named in code: 0 · ended: answered · controller 281063a2d8dd03db…

    The controller is a velocity-command waypoint follower. I rewrote it from the supplied stabilizer.js after that baseline failed all four smoke flights.

    • Gates: For each gate it first lines up at a point 0.5 m before the gate plane, at the gate's height and z. It waits until the position error is small and the drone is nearly still. Then it crosses at a limited x speed of about 1 m/s while holding y and z. If it is more than 0.25 m off in y/z, it stands off at 0.75 m instead. I added that after two gate-0 collisions on random seeds.
    • Control law: Position error sets a clamped desired velocity. A proportional loop on velocity error sets the desired acceleration. That acceleration becomes roll and pitch, rotated by yaw, and a thrust value scaled by tilt. Thrust has a small integral term to absorb the unknown payload and motor loss. Yaw is held at zero.
    • Landing: It moves over the pad at 0.6 m and starts descending once it is within 0.12 m horizontally and slow. The descent speed is limited and gets slower near the floor. It cuts thrust in half at touchdown so it doesn't bounce. It aborts the descent if it drifts more than 0.35 m off the pad.

    I chose velocity commands over the baseline's position PD because they let me cap speeds near the gates and descend smoothly. The earlier settle thresholds were too strict, so the drone hovered near the pad and ran out of the 25 s limit. I loosened them.

    I did not check the final version on a fresh random batch. The version before the last change passed 6 of 8 random flights. After the last change I flew only the two seeds that had collided and the four smoke flights, and all six passed. Some earlier runs finished at about 21 s, so timing margin may be thin on some seeds.

  • easy.none.1 · 58 of 64 fresh · 15 of 16 practice · 13 turns · 8 fly calls
    Quoted its recipe: no · recipe words named in code: 0 · ended: answered · controller e0af14e95898d8d0…

    The controller is a cascaded waypoint follower. I started from the baseline stabilizer, which failed all 4 smoke flights, and replaced its position-PD with a velocity loop on each axis. The velocity loops set the desired tilt, and altitude is controlled by thrust with a slow integral term to absorb the unknown payload and weak motor.

    For each gate it first holds about 0.4 m in front of the gate plane and lines up in y and z. Once it is within about 0.1 m laterally and moving slowly, it locks and drives straight through to 0.5 m beyond the gate at a reduced speed. Aligning first matters because the opening leaves only about ±0.125 m of lateral clearance for the body.

    After the third gate it flies to a point above the pad. It descends slowly once it is close and slow enough, and it can abort the descent if it drifts off the pad. The altitude integral is frozen near the ground.

    The baseline failed because its settle conditions were too strict for gusty wind. Loosening those conditions fixed the stuck-before-gate and stuck-above-pad time-outs I saw.

    Two caveats:

    • Flights were not exactly repeatable. One seed timed out and then landed on a re-fly of identical code.

go run ./examples/squeeze -job examples/squeeze/jobs/recipe-scramble-easy.json -api messages -model claude-sonnet-5-5 -design design.json

The cost. The 40 agents' 478 model calls cost $6.24 at the list prices checked on 2026-11-07 (a million tokens: $2 of prompt read fresh, $2.50 written to the prompt cache, $0.10 read from it, $10 written by the model; EXTERNAL · official docs ↗), computed from the token counts each stage's run.json records. A 2-call check before the run that the prompt cache worked brings it to $6.25. 92% of the prompt tokens were read from the prompt cache (the model's provider keeps the start of a long conversation it has already read, and charges a twentieth of the fresh price to read it again), which is what kept the cost low.

A tier is the daemon's configuration and the provider's evidence plus its startup checks, never hardware attestation.

10Check it yourself

Beside this page: experiment.json (the stages in order, the registered rule, the list prices), evidence.json (every number this page states) and, under stages/baseline/ and stages/recipe/, each stage's run as it wrote it: bundle.jsonl.gz (every run, signed), harness.pub (the public half of the stage's signing key), fresh.json (the sealed set, revealed), run.json (the run's own unsigned account: times, token counts, each agent's turns; its model_base is the local relay that enforced the spending cap, not where the model ran), transcripts.jsonl.gz (every agent's whole conversation, its reasoning summaries and tool calls included), and the evidence.json and agents.json derived from them. From a clone of the repository:

go run ./examples/squeeze -job examples/squeeze/jobs/recipe-scramble-easy.json -staged -verify -out docs/examples/squeeze-recipe

That checks every signature in both bundles and every record against the request and answer stored with it, the leak scans, that every grading run held the sealed set whose SHA-256 the run committed to, that both stages were made under the design the program writes and flew the same set, that each agent's record follows from its transcript and its signed grading runs, and that evidence.json, this page and the method page are exactly what those files state: the intervals and the rule's outcome are computed again, not read. It starts no sandbox and calls no model. Change one byte of a bundle and it refuses.

Run it again. It needs docker with gVisor and the images make docker-images builds, an Anthropic API key in ANTHROPIC_API_KEY, and a token budget the program enforces. Seal a fresh set first, then run each stage on it; -paid is the program's consent to spend, and it refuses to start without it:

J=examples/squeeze/jobs/recipe-scramble-easy.json
go run ./examples/squeeze -job $J -seal fresh.json
go run ./examples/squeeze -job $J -api messages -model claude-sonnet-5-5 -paid -max-tokens 90000000 \
  -fresh fresh.json -fresh-sha256 <its SHA-256> -groups none -out baseline
go run ./examples/squeeze -job $J -api messages -model claude-sonnet-5-5 -paid -max-tokens 90000000 \
  -fresh fresh.json -fresh-sha256 <its SHA-256> -groups recipe,scrambled -build 16 -out recipe

Words used on this page

Model
An AI program, trained on huge piles of examples, that writes answers, text or code.
Model id
The exact version name of a model that a program asks for, so the same one can be asked for again.
Agent
A model working in a loop on its own: write, run, look, try again.
Sandbox
The walled-off place where untrusted code runs.
Harness
The program that hands out each task, runs it and grades it. Here, examples/squeeze.
Controller
The program that flies the drone: called 100 times a simulated second with sensor readings, it answers with thrust, tilt and turn.
Baseline
The plain controller every agent started from, the same for every group.
Token
The unit a language model reads and writes in; a short word is usually one.
Recipe
An earlier AI's whole method on this course, in 32 tokens.
Scrambled recipe
The same words in a shuffled order: the control for "does the order matter?".
Control group
A group given everything except the thing being tested.
Seed
One number that fixes a random draw, so the same shuffle or the same flight can be made again exactly.
Practice flights
The 16 flights the earlier AI tuned itself on; graded here too, but not the measure.
Smoke flights
The 4 flights the course names for a quick check, open to every agent.
Fresh, or sealed, flights
The 64 flights no agent saw, drawn at random and fingerprinted before the run.
SHA-256
A 64-character fingerprint of some bytes: the same bytes always give the same one, a changed byte a different one.
Points
Percentage points of the fresh flights; one flight of 64 is about 1.6.
Noise
The part of a score that is luck; a difference "within noise" is one luck alone could have made.
Resampling
Drawing a group's agents again at random, with repeats, many times, to see how far a difference could move.
95% and 90% intervals
The ranges that hold the middle 95% and 90% of those resampled differences.
Registered rule
The rule for reading the result, fixed before the run.
Messages API
The way a program sends the model a request over the internet and reads its answer.
Prompt cache
The provider's copy of the start of a conversation it has already read, charged at a twentieth of the fresh price.
Bundle
One file holding every run's signed record for a stage, one line a record.
Run record
plimsoll's signed statement of one run: digests of what went in and what came out, where it ran, and when (INTERNAL · glossary →).
